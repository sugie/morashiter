インシデント公開 API：バケツ方式の静的 JSON

作成 2026-11-09 ／ 基準：main 064328a（PR #12 マージ後）／ 状態：計画（承認済みの方針「バケツ方式」で進める。実装は未着手）／ 関連：docs/plans/paypal-extension-implementation-plan.html（WP1〜WP3）、docs/plans/paypal-extension-api-db-design.html（5.1）、docs/plans/chrome-extension-notice-verification.html

要点
  • 拡張は、閲覧中のサイトの登録ドメイン（例：tour.club-t.com → club-t.com）の SHA-256 を手元で計算し、その先頭2文字だけを使って、静的ファイル https://www.morashiter.com/api/v1/buckets/3f.json を取得する。照合は手元で行う。
  • サーバー（CDN）に届くのは「3f」だけ。世界中のドメインの 1/256 が同じ値になるので、どのサイトを見ているかは分からない（k-匿名性。Google セーフブラウジングや Have I Been Pwned と同じ考え方）。
  • バケツは中身が空でもすべて置く（404 を出さない）。登録があるかどうかも通信からは分からない。
  • 件数が増えたら、使う文字数を 2 → 3 → 4 と増やす。文字数は index-meta.json に書くので、拡張の更新は要らない。
  • サーバーの API やコンテナは増やさない。今の公開の仕組み（msgn → S3 → CDN）に、ファイルの出力を足すだけ。

1. なぜバケツ方式か

方式プライバシー規模判断
A. 全件を1ファイル（merchant-index.json）◎ 何も送らない× 数万件で数 MB。毎回の更新が重い採らない
B. ドメインごとのファイル（domains/<ドメインのハッシュ>.json）× ハッシュから元のドメインが分かる（主なドメインを並べた表で逆引きできる）。404 で登録の有無も漏れる◎採らない
C. ハッシュの先頭で分けたバケツ○ 先頭の数文字だけが届く。すべてのバケツがあるので登録の有無も漏れない◎ 文字数で調整できる採る
通販サイトのドメインの数先頭の文字数ファイルの数1ファイルあたり（目安）
〜数千（ハッカソン時点は数件）2256〜十数件
〜10万34,096〜25件
〜100万465,536〜15件

2. 全体の流れ

[管理画面 /admin（既存の IP 制限・ログイン）]
  通販サイトのドメインを登録：host → 会社（根拠 URL つき）          … WP1
  インシデントの承認時に会社を結び付ける（incidents.company_id）      … WP2

[公開：msgn（既存の SitePublisher）]
  PublicSnapshotBuilder … snapshot.json に "merchants" を追加           … WP3
     （通販サイトのドメインが変わっただけでも、スナップショットのハッシュが変わり、公開が「変更なし」で飛ばされない）
  Node のビルド（prototype/scripts）… dist/api/v1/index-meta.json と buckets/00〜ff.json を出力
  verify-static.mjs … 許可リストにこの2種類だけを追加し、形式を検証
  SiteUploader … JSON の Content-Type と Cache-Control。release.json より前にアップロード
  CdnPurger（既存のまま全体を削除）→ release.json の読み戻しで確認

[利用者の Chrome（拡張）]                                              … WP4
  1. GET /api/v1/index-meta.json（release_id と prefix_length）。数時間ごと
  2. タブのホスト → 登録ドメイン → SHA-256 → 先頭 prefix_length 文字
  3. GET /api/v1/buckets/<先頭>.json（release_id ごとに chrome.storage.local に保存して再利用）
  4. バケツの中で、ホストの完全一致を探す → バッジとポップアップ

3. ファイルの形式

3.1 /api/v1/index-meta.json

{
  "schema_version": "merchant-meta.v1",
  "release_id": "a1b2c3d4e5f6",      // release.json と同じ値
  "data_as_of": "2026-11-08",
  "prefix_length": 2,                // 2〜4。サーバーの設定値
  "hash": "sha256",
  "key": "registrable-domain"        // ハッシュする文字列：小文字・末尾ドットなしの登録ドメイン
}

3.2 /api/v1/buckets/3f.json

{
  "schema_version": "merchant-bucket.v1",
  "release_id": "a1b2c3d4e5f6",
  "prefix": "3f",
  "domains": {
    "club-t.com": {                          // 登録ドメイン（SHA-256 の先頭が "3f" のもの）
      "hosts": ["club-t.com", "www.club-t.com", "tour.club-t.com"],  // 完全一致で照合するホスト
      "company": "クラブツーリズム株式会社",
      "incident_ids": ["INC-028"]
    }
  },
  "incidents": {                             // このバケツの domains が参照するものだけ
    "INC-028": { "id", "name", "company", "type", "date", "disclosure", "quantity",
                 "dataType", "status", "source", "contact" }   // 公開サイトの snapshot と同じ項目
  }
}
  • 中身が無いバケツも "domains": {} で置く。
  • 入れるのは「有効な通販サイトのドメイン × 会社 × 承認済みで撤回されていないインシデントの最新版」だけ。撤回したものは入れない。
  • キーと行の順番は固定する（同じ入力なら同じファイル。公開の「変更なし」の判定が効く）。ビルドした時刻は入れない。
  • 登録ドメインそのものは平文で入れる。どの店舗に事故の情報があるかは、もともと公開サイトで公開している情報なので問題ない。守るのは「利用者がどこを見ているか」。

3.3 配信の設定

パスContent-TypeCache-Control
api/v1/index-meta.jsonapplication/json; charset=utf-8public, max-age=300
api/v1/buckets/[0-9a-f]{2,4}.json同上public, max-age=600

公開のたびに CDN のキャッシュを全体削除する（既存の動き）ので、長くても数分で新しい内容になる。拡張は release_id が変わったときだけ、バケツを取り直す。

4. 拡張での照合

  1. タブの URL からホストを取り出す（今の host.js のまま）。
  2. 登録ドメインを求める。公開サフィックスの一覧は、段階1で作った services/mrst/resources/data/public_suffixes.txt と同じ内容を、拡張に同梱する（src/public-suffixes.js）。両方が同じ内容であることはテストで確かめる。
  3. crypto.subtle.digest("SHA-256", …)（ブラウザの標準機能。外部のライブラリは使わない）で 16 進数に変換し、先頭 prefix_length 文字を取る。
  4. バケツを取得する（保存済みで release_id が同じならそれを使う）。
  5. domains[登録ドメイン].hosts にタブのホストが完全一致で含まれるときだけ「情報あり」。登録ドメインが同じでも、一覧に無いホストは「登録情報なし」。
    理由：myshopify.com や shop-pro.jp のように、1つのドメインの下に別々の店舗が並ぶサービスがある。ドメイン単位で一致させると、無関係な店舗に表示が出る。
  6. 取得の失敗、タイムアウト（10秒）、形式の誤りは「取得失敗」。「登録情報なし」とは表示しない（今の作りのまま）。

拡張の data-source.js は lookupHost(host) の形を保ったまま、取得する実装に差し替える。タブの監視（monitor.js）とポップアップは変えない。架空の店舗（*.localhost）とデモシナリオは、拡張の中のデータのまま残す。

5. 作業単位（テストを先に書き、失敗を確かめてから実装する）

WP1 通販サイトのドメインの登録 （mrst）

  • テーブル merchant_domains：id, host（一意。小文字・末尾ドットなし・IDN は punycode）, registrable_domain（RegistrableDomain::of で保存時に計算）, company_id（FK）, evidence_url（https のみ）, note, verified_by_admin_id, verified_at, disabled_at, timestamps。
  • 管理画面 /admin/merchant-domains：一覧・登録・無効化（削除はせず disabled_at）。会社は既存の会社から選ぶ（company-choice の部品を使う）。パスワードの再入力はしない（最近の方針に合わせる）。
  • 拒否するもの：IP アドレス、localhost、スキーム・パス・ポートつき、公開サフィックスだけ（co.jp）、別の会社で登録済みのホスト、http の根拠 URL。

WP2 インシデントと会社の結び付け （mrst）

  • incidents.company_id（nullable, FK）を追加。
  • 承認時に、審査 → 公式文書 → 公式ドメイン → 会社 とたどって自動で入れる（IncidentApprovalController）。
  • 既存分は php artisan incidents:link-companies（既定は確認だけ。--apply で書き込む）。たどれないもの（手作業で入れた分など）は、訂正版の画面で会社を選べるようにする。

WP3 バケツの生成と配信 （mrst と prototype）

  • PublicSnapshotBuilder："merchants" を追加する（登録ドメイン → ホストの一覧・会社・インシデントの ID）。対象の判定は PHP 側の1か所で行う。
  • Node のビルド：prefix_length（MSGN_MERCHANT_PREFIX_LENGTH、既定 2）で、index-meta.json と、すべてのバケツを出力する。
  • verify-static.mjs：許可リストに api/v1/index-meta.json と ^api/v1/buckets/[0-9a-f]{2,4}\.json$ だけを追加する。バケツの数が 16^prefix_length であること、JSON として正しいこと、localhost などの禁止文字列が無いことを検証する。
  • SiteUploader：3.3 のヘッダー。アップロードの順番は「アセット → JSON → HTML → release.json」。
  • 公開サイトの画面（CSP connect-src 'none'）は変えない。JSON を読むのは拡張だけ。

WP4 拡張の対応 （extensions/chrome）

  • manifest.json：host_permissions: ["https://www.morashiter.com/*"] だけを追加する。tabs と storage はそのまま。コンテンツスクリプトは使わない。
  • src/remote-data-source.js（新規）：meta の取得 → 登録ドメイン → ハッシュ → バケツの取得 → 完全一致。chrome.storage.local に release_id ごとに保存する。meta は6時間ごとと「再確認」のときに取り直す。
  • src/public-suffixes.js（新規）：サーバーと同じ一覧。
  • 拡張の名前と説明から「架空データ・通信なし」を外し、「www.morashiter.com から公開データだけを取得します。閲覧中の URL は送りません」と書く。ポップアップの右上の表示は、「登録情報なし」のときは出さない（Windows での確認で気付いた点）。
  • README（英語と日本語）：取得するもの・送らないもの・権限の理由。

WP5 提出用の文書 （docs）

  • プライバシーの説明（英語）：「先頭2文字だけを取得し、どのサイトを見ているかは送らない」を図で説明する。
  • 審査員向けの手順（フォルダーから読み込む方法）。

6. プライバシーと安全

心配対策
閲覧しているサイトが分かる先頭2〜4文字だけが届く。同じ値になるドメインが世界中に多数ある。すべてのバケツを置くので、登録の有無も分からない。
アクセスの記録から利用者が分かるCDN には通常のアクセスの記録（IP アドレス）が残る。拡張は Cookie もクエリも付けない。ユーザーごとの ID は持たない。
JSON の改ざん・なりすましhttps のみ。取得先は www.morashiter.com に固定し、設定やデータで変えられないようにする。表示は textContent だけ（今の作り）。
誤った情報が出る承認済み・未撤回・最新版だけを入れる（公開サイトと同じ門）。出典の URL と確認日を表示する。
無関係な店舗に表示が出るホストの完全一致だけ。公開サフィックスだけの登録は拒否する。
サーバーの負荷静的ファイルと CDN だけ。api1 への通信は増えない。

7. テスト

対象正常異常・境界
WP1（PHPUnit）登録・一覧・無効化、登録ドメインの計算重複、IP、localhost、パスつき、co.jp、http の根拠、別の会社のホスト、253文字、xn--、大文字・末尾ドット、無効な管理者、許可外の IP
WP2（PHPUnit）承認で会社が付く、既存分を --apply で埋めるたどれない場合は null、確認だけでは書き込まない、付いているものは上書きしない
WP3（PHPUnit と node --test）ドメインからインシデントが引ける、同じ会社の複数ドメイン、バケツの数が 256無効化したドメインは出ない、撤回・未承認は出ない、0件でも全バケツがある、同じ入力で同じハッシュ、許可リスト外のファイルは拒否
WP4（node --test と Playwright）meta → バケツ → 完全一致で「情報あり」、release_id が同じなら取り直さない同じ登録ドメインの未登録ホストは「登録情報なし」、取得失敗・タイムアウト・形式の誤りは「取得失敗」、閲覧中の URL がどの通信にも含まれない、www.morashiter.com 以外へは通信しない
サーバーと拡張の一致同じ登録ドメインから、PHP と Node と拡張が同じハッシュ・同じ先頭を出すこと（固定の例で確かめる）。公開サフィックスの一覧が同じ内容であること。

既存のテスト（CI の mrst-phpunit と prototype のテスト）は毎回すべて通す。実行していないテストを、確認済みとは書かない。

9. デプロイと戻し方

  • いつもの手順：PR をマージ → PC で --push つきでイメージを作る → compose.env → pull → migrate → mrst-restart → 公開実行。
  • マイグレーションは追加だけ（新しいテーブルと nullable の列）なので、イメージを前のものに戻しても旧コードで動く。
  • バケツの出力に問題があれば、前のイメージに戻して公開実行し直す（公開の仕組みは、失敗すると前の公開内容をアップロードし直す）。

10. 決めること

  1. デモで使う通販サイトのドメイン：API で配る最初の数件を選ぶ。根拠となる公表資料と、公開中の記録の内容が正しいことを先に確かめる。
  2. club-t.com の扱い（INC-028 の日付の誤りは 11/13 の後に直す方針）：
    • 推奨：直すまでは club-t.com を通販サイトのドメインに登録しない。拡張に同梱した記録（公表日は正しく 2026-10-31）で、デモを続ける。
    • 別案：先に INC-028 の公表日だけを訂正版で直してから登録する。
  3. 拡張のソースの公開先：規約では公開リポジトリが必要。今は push しない決まりなので、提出の前に置き場所を決める。
  4. Chrome ウェブストア：フォルダーから読み込む方法だけにするか、限定公開の申請も並行して出すか。

11. ハッカソン後に回すこと

  • INC-028 の公表日の訂正と、AI が一覧の別の項目の日付を拾った原因の調査。
  • 登録ドメインの下のすべてのホストを同じ会社として扱う印（include_subdomains）。共用サービスのドメインは拒否する一覧と合わせて入れる。
  • 公開サフィックスの一覧を、正式の一覧（Public Suffix List）から自動で更新する。
  • 件数が増えたときに prefix_length を 3 に上げる手順（設定を変えて公開実行するだけ。拡張はそのまま）。
  • PayPal の案内の条件（paypal_option）を、バケツの中に入れる（設計案 5.1 の条件のまま）。
