1. 目的と範囲

買い物をしている人が、EC サイトの運営会社について公式に公表された漏えい事故の事実を、決済の前に出典つきで確認できるようにする。決済は PayPal Sandbox の自前デモ店舗で、利用者の明示的な承認のもとで行う。

範囲に含める範囲に含めない
  • Chrome 拡張（Manifest V3、サイドパネル、英語／日本語）
  • EC ドメインとインシデントの対応表（静的 JSON）と、その管理画面
  • AI の購入前メモ API（承認済みの事実だけを入力）
  • デモ店舗（架空企業）と PayPal Sandbox の注文作成・検証・capture
  • 英語の README・プライバシー説明・テスト手順、動画、Devpost 説明
  • 本番決済（live 環境）。設定で起動を拒否する
  • 第三者 EC サイトの決済の置き換え、ページの書き換え
  • 企業の安全度スコア・ランキング・法的評価（docs/mvp-scope.md の対象外）
  • 閲覧履歴の収集、拡張でのアクセス解析
  • Chrome ウェブストアへの公開（必要なら別途承認）
  • Agent Toolkit／MCP を使うエージェント購入（P2 の発展案。docs.paypal.ai の確認後に判断）

2. 前提

2.1 ハッカソン規約（2026-11-01 確認、rules）

  • PayPal 開発者プラットフォーム（無料の Sandbox）と任意の AI を組み込むこと。既存プロジェクトは応募期間（10/1〜）に大きく更新し、その内容を説明すれば可。
  • 審査員が実際に動かせること（ホストしたデモか、完全な手順）。12/15 まで無料・制限なしで利用可能にする。Sandbox のログイン情報も手順に含める。
  • 公開リポジトリに OSS ライセンス（About 欄に表示）。動画は 3 分未満・YouTube 公開・第三者の商標や著作物なし。提出物は英語（または英訳）。
  • 審査は合否判定のあと、技術・デザイン・インパクト・革新性・プレゼンを等しい重みで評価。

2.2 PayPal の仕様（2026-11-01 確認）

  • JS SDK v6：Sandbox は https://www.sandbox.paypal.com/web-sdk/v6/core。createInstance({ clientId, components: ["paypal-payments"], pageType: "checkout" }) → findEligibleMethods({ currencyCode }) → createPayPalOneTimePaymentSession({ onApprove, onCancel, onError }) → クリックで session.start({ presentationMode: "auto" }, createOrder())。createOrder は { orderId } を返す。capture 前にサーバーで注文内容を検証する。
  • Orders v2：https://api-m.sandbox.paypal.com、OAuth2 client credentials。POST /v2/checkout/orders、GET /v2/checkout/orders/{id}、POST /v2/checkout/orders/{id}/capture。作成と capture は PayPal-Request-Id（冪等化）に対応。

2.3 既存の基盤

  • mrst（Laravel、FrankenPHP）が api1 の 153.127.200.100:8082 で動き、LB 経由で api.morashiter.com を配信。/admin だけが EnsureAdminIpAllowed で IP 制限。公開 API は GET /api/health のみ。
  • 公開サイトは msgn が S3＋CDN に静的配信。配信ファイルは prototype/scripts/verify-static.mjs の許可リストで制限され、Content-Type と Cache-Control は SiteUploader が決める。
  • さくらの AI Engine 連携（SakuraIncidentAnalyzer、AiUsageBudget の日次上限、ai:check）。
  • official_domains（host → company）はコーポレートサイトのホスト。EC サイトのドメインとは別に管理が必要。

4. 本番への影響と保護策

心配対策
既存機能を壊す追加は新しいルート・テーブル・クラスだけ。既存テーブルへの変更は incidents.company_id（nullable）の追加のみ。既存テスト全件（CI mrst-phpunit）を毎回通す。
決済機能が本番で誤動作DEMO_SHOP_ENABLED=false が既定。PAYPAL_MODE は sandbox 以外を受け付けず、PayPal のベース URL はコード側で Sandbox に固定（env では変えられない）。
AI の費用が増えるASSIST_ENABLED=false が既定。購入前メモは公式発表解析とは別の日次上限（ASSIST_MAX_PER_DAY、初期 50）。同じ入力はキャッシュから返す。上限到達時は AI を使わない定型文を返す。
公開 API への負荷・悪用Laravel のレート制限（IP ごと）。/api/v1/* は読み取りと Sandbox の注文だけ。管理系はすべて既存の /admin（IP 制限）配下。
公開サイトの配信追加は api/v1/merchant-index.json 1 ファイル。許可リストと Content-Type を明示的に追加し、他のファイルは今までどおり拒否。release.json の確認手順は変えない。
サーバー資源新しいコンテナは作らない。PayPal と AI への外向き通信が増えるだけ（タイムアウト 10〜30 秒、再試行は既存方針どおり最小限）。
戻し方まず機能フラグを false にして mrst-restart。それでも足りなければ compose.env のイメージを前のダイジェストに戻す。マイグレーションは追加のみなので戻さなくても旧コードで動く。

  • テスト（先に書く）：正常（登録・一覧表示・無効化）／異常（重複ホスト、http の根拠 URL、IP アドレス、localhost、パス付き入力、パスワード誤り、無効な管理者、許可外 IP）／境界（253 文字のホスト、xn-- の IDN、大文字・末尾ドット、co.jp のような公開サフィックスだけの入力は拒否）。
  • 完了条件：上記テストが通り、既存テスト全件が通る。

WP2 インシデントと会社の結びつき

  • 追加：incidents.company_id（nullable、FK）。承認時に review → official_document → official_domain → company から自動設定（IncidentApprovalController）。既存分は Artisan コマンド incidents:link-companies（既定は --dry-run、--apply で書き込み）で埋める。手作業の 7 件など、たどれないものは管理画面の「訂正版を作成」と同じ画面で会社を選べるようにする。
  • テスト：承認で会社が付く／たどれない場合は null のまま／dry-run は書き込まない／既に付いているものは上書きしない／撤回済みも対象外にしない（表示側で撤回として扱う）。

WP3 merchant-index.json の生成と配信

  • 追加：App\Services\Publishing\MerchantIndexBuilder（PublicSnapshotBuilder と同じく決定的：キーと行の順を固定、ビルド時刻を含めない）。SitePublisher がビルド結果に api/v1/merchant-index.json を加えてからアップロード。SiteUploader に application/json; charset=utf-8・public, max-age=600 を追加。verify-static.mjs の許可リストにこのパスだけを追加。
  • 形式：6 章 6.1。domains は「有効な merchant_domains × 会社 × 撤回されていないインシデント」。撤回は withdrawals に入れ、事実としては返さない。
  • テスト：正常（ドメインからインシデントが引ける、同じ会社の複数ドメイン）／異常（無効化したドメインは出ない、撤回済みは withdrawals のみ、未承認は出ない）／境界（0 件、会社のないインシデント、同じ入力で同じハッシュ）。prototype 側：許可リスト外のファイルは引き続き拒否、追加ファイルは JSON として妥当。

WP4 AI 購入前メモ API

  • 追加：Api\AssistController、App\Services\Ai\PurchaseNoteGenerator（さくら AI、既存の区切り・指示無視の方式）、PurchaseNote（出力の検証）、テーブル assist_notes（キャッシュ）、レート制限 assist、AiUsageBudget を provider 名 sakura-assist と別上限で使う。ai:check に購入前メモの使用量を表示。
  • 出力ルール：facts[] は各要素に入力のインシデント ID と、その公式発表 URL を必ず持つ（入力にない URL は拒否）。general_tips[] は一般的な注意で、事実と混ぜない。「安全」「危険」「問題ない」などの断定語を含む出力は拒否。AI が使えない・失敗・上限到達のときは、定型の事実一覧（generated_by: "template"）を返す。
  • テスト（HTTP はモック）：正常・キャッシュ命中・英語／日本語／異常（未知の ID、撤回済み ID、ID 0 件・11 件以上、未知の URL を含む応答、JSON 不正、断定語、AI の 429・5xx・タイムアウト、上限到達、レート制限）／境界（ID 10 件、同じ ID の重複）。

WP5 デモ店舗と PayPal Sandbox 決済

  • 追加：config/demo_shop.php（架空企業「Northwind Goods (fictional)」と商品 2〜3 点、価格は USD の文字列で固定）、DemoShopController（一覧・商品・完了画面）、Blade（JS SDK v6）、App\Services\Payments\PayPalSandboxClient（OAuth トークンをキャッシュ、ベース URL は定数で Sandbox 固定）、DemoOrderService、Api\DemoOrderController（create／capture）、テーブル demo_orders、デモ用の架空インシデントと /demo-shop/merchant-index.json（設定ファイルから生成。本番の公開データには入れない）。
  • 注文作成：ブラウザからは product_id と client_request_id（UUID）だけを受ける。金額・通貨・商品名はサーバーのカタログから。PayPal には PayPal-Request-Id = client_request_id で POST /v2/checkout/orders（intent CAPTURE）。応答の id を demo_orders に記録し { orderId } を返す。
  • capture：demo_orders を行ロック → 自分が作った注文か・未 capture かを確認 → GET /v2/checkout/orders/{id} で金額・通貨・状態（APPROVED）を照合 → POST .../capture（PayPal-Request-Id 付き）→ capture の status が COMPLETED、金額・通貨が一致することを確認して記録 → 検証済みの値だけを返す。
  • 画面のヘッダー：デモ店舗だけ CSP を付ける（script-src 'self' https://www.sandbox.paypal.com を起点に、PayPal が実際に必要とするホストを実装時に確認して追加。frame-src・connect-src も同様）。
  • テスト（PayPal はモック、最後に Sandbox で 1 回通し）：正常（作成 → capture → 完了）／異常（ブラウザから金額を送っても無視、存在しない商品、他人の注文 ID、二重 capture、PayPal の 4xx・5xx・タイムアウト、capture の金額不一致、PAYPAL_MODE=live での起動拒否、DEMO_SHOP_ENABLED=false で 404）／境界（同じ client_request_id の再送で注文が増えない、同時 capture 2 本で 1 回だけ成功）。

9. セキュリティ・プライバシーの確認項目

  • 拡張は閲覧中の URL を外部へ送らない（ネットワーク呼び出しは 2 つの JSON 取得と、ID だけの POST）。Playwright のテストで、送信されたリクエストの中身を確認する。
  • 拡張に鍵・トークンを置かない。PAYPAL_CLIENT_SECRET と AI のキーはサーバーの env のみ。
  • 拡張の CSP は script-src 'self'; object-src 'none'。表示は textContent のみ。
  • AI の入力は承認済みデータだけ（ページ本文は入れない）。出力は検証してから返す。
  • 決済：金額はサーバーのカタログ、冪等キー、行ロック、capture 前後の照合、live 環境の拒否。
  • 企業の評価はしない。各表示に出典・データ時点・訂正窓口を付ける。訂正は既存の「訂正版を作成」の運用。
  • デモの企業・インシデントは架空であることを画面に明示し、本番のインデックスに混ぜない。
  • ログに購入者の情報や PayPal の応答本文を残さない（注文 ID と状態だけ）。

12. デプロイと戻し方（既存の Runbook に従う）

  1. PC：git checkout main && git pull → git log -1 --oneline で対象コミットを確認 → bin/mrst-release-images.bash --push（タグがコミットと一致することを確認）。
  2. api1：/etc/mrst/compose.env の 2 行を更新（旧値はコメントで残す）→ sudo grep -v '^#' /etc/mrst/compose.env | grep IMAGE で web／worker の取り違えがないか確認。
  3. api1：pull → --profile release run --rm migrate（追加テーブルと列）→ mrst-restart。
  4. 確認：/up が 200、route:list --path=demo-shop と --path=api/v1 にルートがある、フラグ off で /demo-shop が 404、ai:check。
  5. 2 回目のデプロイ後に env を設定（人が入力）→ mrst-restart → Sandbox で購入 1 回 → 「公開実行」で merchant-index.json を配信 → https://www.morashiter.com/api/v1/merchant-index.json を確認。

戻し方：フラグを false → mrst-restart。コードを戻す場合は compose.env を旧ダイジェストに戻して pull・mrst-restart。追加テーブルは残してよい。

13. リスクと対策

リスク対策
EC ドメインの登録が少なく、デモ以外で「該当なし」ばかりになるデモ動画は架空のデモ店舗で完結させる。実在企業は根拠つきで登録できた分だけ載せ、未検出の表示文言で誤解を防ぐ。
公開データの誤り（重複・単位なし・根拠資料のずれ）がデモに映る11/8 までに INC-015/017/019/020 を訂正。動画では実在企業のデータを映さない。
JS SDK v6 の CSP や挙動が想定と違う11/5 にデモ店舗を先に本番へ（フラグ off で配置、Sandbox で動作確認）。公式サンプル（paypal-examples/v6-web-sdk-sample-integration）と照合。
さくら AI の英語出力の品質英語は定型文＋AI の要約を短くする。品質が足りなければ gpt-oss 系モデルへの切替を検討（さくら AI Engine 上で、要確認）。
「大きな更新」と認められない新規部分を README と Devpost に具体的に列挙（コミット範囲 10/1 以降）。
審査期間中の停止毎朝の確認に追加。障害時はフラグで切り分け、Devpost の手順に連絡先を書く。
未 push の手元の変更との衝突着手前に push してもらい、その上に積む。
