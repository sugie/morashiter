1. 現状（2026-11-07 の管理画面）

  • ダッシュボード：「公式発表が見つからない」21件、「公式発表の取得失敗」2件（グッドスマイルカンパニー #42、NEC #24、どちらも http_non_200）。
  • ニュースのクローラーは、11月の記事も取り込めている（Security NEXT の RSS を api1 から取得して確認）。止まっているのは、その先の「個別の発表を見つける」段階。
  • 2026-11-06 に入れた AI 探索：
    • 本番で動作した。
    • アテニアでは、お知らせ一覧の「分類で絞り込むリンク」（?category=…）を候補に拾ってしまった。
    • 状態の表示が「候補あり（AI照合なし）」となり、AI を使わなかったのか、AI が照合して該当なしと判断したのかを区別できなかった。
  • 例：グッドスマイルカンパニーの発表は、サポートサイト support.goodsmile.com にある。登録済みの公式ドメインは www.goodsmile.com で、ニュースのリンクもそちらだった。

2. 原因の分類

#原因例今の仕組みで起きること
A発表が別のホストにある（サポート・IR・コーポレートなどのサブドメイン、または別ドメイン）グッドスマイル（support.）、楽天（corp. は登録済みだが発表は別の場所の可能性）登録済みのホストと完全一致するサイトしか取得しないので、たどり着けない（安全のための仕様）
Bトップページの取得に失敗する（403・503 など、自動アクセスの拒否）グッドスマイル #42、NEC #24failed になり、AI 探索の対象にもならない
C発表が一覧の奥にあり、見出しに事件の語が無い県・市の「報道発表」「新着情報」、企業の「重要なお知らせ」AI 探索で一部は拾えるが、行政サイトの一覧の語（報道発表・記者発表など）が判定の条件に無い
Dルールで集めた候補にノイズが多いアテニアの ?category=…人が見ても役に立たない候補が並び、確認に時間がかかる
E元ニュースの情報を探索に十分使えていないニュース本文に発表の題名や日付が書かれている今の AI 探索が使うのは、ニュースの題名と公開日だけ
F人が探す作業に補助が無い管理者が検索サービスで探して URL を貼っている1件あたり数分かかる

4. 対応策の詳細

① 「検索で探す」リンク（P1）

  • 「公式発表を見つけられなかった候補」の各行に、ブラウザで検索を開くリンクを出す： 
    https://www.google.com/search?q=site:<登録済みドメインの登録ドメイン部分> <ニュースの題名から組織名を除いた語>
  • site: には、ホストではなく登録ドメインの部分（例：goodsmile.com）を使う。こうすると support.goodsmile.com も検索結果に出る。
  • サーバーからは何も送らない。管理者のブラウザで開くだけなので、外部 API の契約や鍵は不要。2026-11-06 の「Web 検索 API は使わない」という決定とも矛盾しない。
  • 行政サイト向けに、「報道発表」を語に足したリンクも出す。

② 関連ホストとして、その場で登録して追加（P1）

  • 「公式発表を追加」の URL に、未登録のホストを貼ったときの動き：
    • そのホストが、選んだ組織の登録済みドメインと同じ登録ドメイン（例：support.goodsmile.com と www.goodsmile.com は、どちらも goodsmile.com）なら、確認のチェックボックスを出す。
      • チェックボックスの文言：「support.goodsmile.com を〇〇の公式ホストとして登録し、このURLを追加する」
    • 同じ登録ドメインでない（まったく別のドメイン）場合は、今までどおり「選択肢に公式ドメインがない場合」から先に登録させる。
  • 登録ドメインの判定には、公開サフィックスの一覧を使う（co.jp・lg.jp などを正しく扱うため）。依存ライブラリを追加する代わりに、固定の一覧をリポジトリに置く方法も検討する（判断事項3）。
  • 登録の記録には、既存の official_domains を使う。メモ欄（note）に「関連ホストとして追加（元：www.goodsmile.com）」と残す。
  • その後の流れ（取得 → AI 解析 → 審査キュー）は、今と同じ。

③ AI 探索の候補を整える（P1）

  • お知らせ一覧から拾うリンクを絞る：
    • リンクの文字に日付か事件の語があるものだけを候補にする。
    • 一覧ページと同じパスで、クエリだけが違う URL（?category=…、?page=2）は、候補から除く。
  • 一覧ページの判定に行政用語を足す：報道発表、記者発表、プレスリリース、新着情報、お知らせ一覧、県政・市政の情報。
  • 状態の表示を分ける：
    • AI を使わなかった：「ルールの候補のみ」
    • AI が照合して該当なし：「AIは該当なしと判断（参考：ルールの候補）」
    • AI の失敗：「AI照合に失敗（参考：ルールの候補）」
    あわせて、取得したページ数と探索した日時を小さく出す。

④ 取得失敗の候補も探す（P2）

  • 対象に status=failed かつ error_code=http_non_200 の候補を加える。
  • トップページが取れなくても、robots.txt・sitemap.xml・典型的な一覧の URL（/news/、/press/、/info/、/release/）から探す。
  • 取得に失敗したときの HTTP ステータス（403・503 など）を探索結果に残し、画面に「自動アクセスを拒否している可能性」と出す。
  • 拒否が続くサイトは、無理に取りに行かない（取得の間隔と回数の上限は、今の設定を守る）。この場合は ① の検索リンクと ② の追加で、人が対応する。

⑤ 関連ホストの候補を自動で示す（P2）

  • AI 探索で取得したページの中から、同じ登録ドメインの別ホストへのリンクを集める。
    • 集める対象：「サポート」「お知らせ」「IR」「重要」などの文字を持つリンク。
  • 探索結果に「関連ホストの候補：support.goodsmile.com」として出す。
    • ボタン：「このホストを登録して探索」
    • 押すと、② と同じ確認をしてから登録し、再探索する。
  • 自動で登録はしない（同じ登録ドメインでも、別会社のサイトや外部サービスのことがあるため）。
  • DB の変更：official_announcement_searches.related_hosts（jsonb、nullable）。

⑥ ニュース本文の活用（P3）

  • 保存してあるニュース本文から、AI に次を抜き出させる。
    • 発表の題名
    • 公表日
    • 組織名
    • 「〜のサイトで公表」といった手がかり
  • 抜き出した語は、③ の点数付けと AI 照合の入力に加える。
  • ニュース本文は「信頼しないデータ」として扱う。AI に URL を書かせない方式は変えない。

6. 守る安全上の決まり

  • 公式かどうかは人が決める：ホストの登録は、人の確認（チェックボックス）を通したときだけ行う。サブドメインでも自動では登録しない。
  • 取得するのは登録済みのホストだけ：探索や取得で、登録していないホストにはアクセスしない（今の UrlPolicy をそのまま使う）。
  • 外部へは何も送らない：① の検索リンクは、管理者のブラウザで開くだけ。サーバーから検索サービスへの通信は無い。
  • AI に URL を作らせない：今の方式（番号で選ばせる、引用が本文にあるかをコードで確かめる）を続ける。
  • 追加・承認・公開は自動にしない。

7. 先に書くテスト（段階1）

対象正常異常・境界
① 検索リンクsite:goodsmile.com とニュースの題名を含むリンクが出る
  • co.jp・lg.jp の登録ドメインを正しく扱う
  • 題名が無い候補でもリンクが壊れない
  • 題名は URL エンコードされる
② 関連ホストとして追加同じ登録ドメインのホストを、確認付きで登録して追加できる。official_domains の会社とメモが正しい
  • 確認が無ければ登録も追加もしない
  • 別の登録ドメイン（例：goodsmile.example）は拒否する
  • co.jp だけが同じ別会社（a.co.jp と b.co.jp）は拒否する
  • IP アドレス・http・トップページは拒否する
  • 二重登録しない
③ 候補の整理
  • 日付のある一覧のリンクは残る
  • 「報道発表」の一覧ページから候補が集まる
  • 状態が3通りに表示し分けられる
  • ?category=・?page= の絞り込みリンクは候補にしない
  • 日付も事件の語も無い一覧のリンクは候補にしない

8. 判断をお願いしたいこと

  1. 段階1（①・②・③）を、今すぐ進めてよいか。
  2. ① の検索リンクの検索先は Google でよいか（Bing などにもできる）。
  3. ② の登録ドメインの判定方法：
    • 公開サフィックスの一覧を固定ファイルとして同梱する（依存を増やさない。推奨）
    • ライブラリを追加する（依存の追加になる）
  4. ④ 以降（取得失敗の候補の探索、関連ホストの候補）を、ハッカソン提出の後に回してよいか。
