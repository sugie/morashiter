msic 公式発表収集 実装計画

ニュースサイトは「事件の発見」にだけ使い、掲載の根拠は企業・行政の一次資料に置く。msic は、msnc が見つけた公式発表リンクの候補を確かめ、一次資料を取得・保存して、msjd（判定）へ渡す。

この文書は実装計画です。msic のコードはまだ書いていません。法的な整理は一般的な検討であり、公開前に法律家の確認を受けます。

1. 方針（2026-10-20 合意）

対象扱い
ニュースサイト（msnc）フィードの見出し・URL・日付と、記事内の外部リンク（公式発表の候補）だけを使う。記事本文は保存しない（2026-10-20 実装済み：抽出結果は本文の文字数だけを返し、証拠ファイルも書かない）。ニュースの見出しやテキストは掲載に使わない。
企業・行政の一次資料（msic）取得して非公開で保存し、事実確認と判定の根拠にする。発表文も著作物なのでそのまま掲載しない。
morashiter.com の掲載件数・対象情報・公表日・対応状況などの事実を自分の言葉で要約し、公式発表へのリンクを付ける。タイトルは企業の発表名か自前の文。引用する場合は引用の要件を守る。

2. 処理フロー

1. 候補の発生（msnc、実装済み）ニュース記事から外部リンクを取り出し、official_link_candidates に pending で記録する。SNS・共有・広告ドメインと同一サイトは除外済み。
2. 取得先の判定候補のホストが「公式ドメイン台帳」に登録済みなら accepted。未登録は needs_review として管理画面に出し、人が企業と公式ドメインを登録する（自動では取得しない）。
3. 一次資料の取得（msic）accepted の URL を SafeHttpFetcher で取得。HTML と PDF を非公開ストレージへ保存し、official_documents を作る。
4. 抽出発表日・タイトル・本文テキストを抽出（HTML は既存の Python 抽出器に official 用アダプター、PDF はテキスト抽出）。
5. 判定へ受け渡しdocument_processing_requests（msjd 計画）へ official_document を登録。判定の入力は一次資料だけ。
6. 掲載人の確認を経た要約＋公式リンクを msgn が静的サイトへ出す（msjd-msgn 計画）。

3. DB

テーブル内容制約
official_link_candidates（実装済み）source_document_id、url、url_hash、host、anchor_text、statusUNIQUE(source_document_id, url_hash)。status を pending / accepted / needs_review / rejected / fetched に広げる
companies（新規）表示名、法人番号（任意）、メモ法人番号は UNIQUE（NULL 可）
official_domains（新規）company_id、host（完全一致）、verified_by、verified_at、noteUNIQUE(host)。登録は管理画面からのみ
official_documents（新規）candidate_id、company_id、url、final_url、content_sha256、content_type、private_object_key、title、published_on、fetched_at、extraction_versionUNIQUE(url_hash, content_sha256)。内容が変われば新しい行（続報・訂正を追える）

4. 取得先の許可（SSRF と誤取得の対策）

  • msic が取得するのは official_domains に人が登録したホストだけ。ニュース記事のリンクだからという理由で自動取得しない（偽サイト・無関係サイトへのアクセスを防ぐ）。
  • 既存の UrlPolicy・SafeHttpFetcher をそのまま使う：https のみ、DNS 解決後のプライベート IP 拒否、リダイレクトごとの再検証、サイズ・時間上限。リダイレクト先も official_domains に含まれる必要がある。
  • robots.txt を尊重し、ホストごとの最低間隔は msnc と同じ HostRateLimiter を使う。
  • 停止スイッチは msnc と同じ MsncFetchGate を共有するか、MSIC_FETCH_ENABLED を別に設ける（未決）。

5. 取得・保存

  • HTML：最大 2 MiB。PDF：最大 10 MiB（企業の「お知らせ」PDF が多いため）。それ以外の Content-Type は取得失敗として記録。
  • 原本は本番の名前付きボリューム（msnc と同じ mrst_evidence）に保存し、のちに非公開オブジェクトストレージへ移す。公開バケットには置かない。
  • 同じ URL を定期的に再確認し（例：公表から 30 日間は 1 日 1 回）、内容が変われば新しい版として保存する。続報・訂正の検出に使う。
  • PDF のテキスト抽出は Python 側（例：pypdf）。依存追加は承認事項。

6. 掲載文の作り方

  • AI は一次資料から「件数・単位・対象情報・公表日・対応状況・問い合わせ先」の候補を構造化して出すだけ。文章の転載はしない。
  • 掲載するのは人が確認した要約と、公式発表へのリンク。漏えい「確定」と「可能性」を区別し、資料の日付時点であることを明記する。
  • ニュースサイト由来の情報（見出し・本文）は掲載データに入れない。発見経路として内部にだけ残す。

7. テスト（TDD）

区分ケーステストデータ期待結果
正常登録済みドメインの候補official_domains に host を登録、HTML fixture候補が accepted → fetched、official_documents が 1 件、原本が保存される
正常PDF の発表小さな PDF fixture（テキスト入り）Content-Type が application/pdf、タイトル・本文が抽出される

異常リダイレクトで台帳外へHttp::fake で 302 → 別ホスト取得失敗（url_policy_violation）、保存なし

8. 実装順序

  1. companies / official_domains / official_documents のマイグレーションとモデル、candidate の status 拡張
  2. 管理画面：needs_review の候補一覧と、企業・公式ドメインの登録（承認者と日時を記録）
  3. FetchOfficialDocument ジョブ（台帳チェック → 取得 → 保存 → official_documents）
  4. official 用 HTML アダプターと PDF 抽出（Python）
  5. 定期再確認と版管理
  6. msjd への受け渡し（document_processing_requests）
