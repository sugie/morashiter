msnc ニュースクローラー実装計画

登録したニュース配信元から記事を継続取得し、取得時点の資料を非公開で保存して、msjdの複数AI判定へ渡す。

設計ブランチ：design/mrst-database。この文書は実装計画です。クローラー実行、DB変更、クラウド設定変更は行っていません。対象媒体や契約条件は未確定のため、実在媒体の取得を開始する設定は含めません。

1. 実装範囲と既存コード

項目方針
初期方式既存のLaravelアプリケーションにArtisanコマンド、Scheduler、データベースキュー、Python＋BeautifulSoupのHTML抽出処理を追加。APIとコードを共用し、msncワーカーを別プロセスで動かす。
取得対象登録済みニュース媒体のRSS/Atomを優先。提供されるAPI、RSSのないHTML一覧は媒体別アダプターで対応。最初は取得が許可された少数の配信元で開始する。
msnc記事発見、URL検証、取得、本文抽出、資料保存、候補選別、判定待ち登録まで。企業の同定や公開承認は担当しない。
msic / msjd / msgnmsicは公式資料を取得。msjdは記事の該当性・企業・事実を合議し、一次資料との照合を行う。msgnは承認済み版を静的HTMLへ配信する。
初期版から除く処理全Web巡回、ログイン・有料壁の回避、JavaScriptブラウザー取得、PDF/OCR、検索エンジン画面のスクレイピング。必要性を計測して別工程にする。

services/api/config/incident_collection.phpには取得上限の設定、AnalyzeIncidentFixtureとIncidentAnalyzerにはローカル資料を単一AIへ渡すひな形があります。現在確認できる範囲では、クロール用モデル・取得ジョブ・定期実行は未実装です。

compose.yamlはPostgreSQLとdatabaseキューを用意していますが、DB名はまだrightsrelayです。新しいmrst設計への移行は別DBで行い、既存データの名称変更・移行を暗黙に実行しません。

既存のdocs/architecture/crawler-and-ai.mdの「全件人手承認」と、今回のテーブル案の「条件付きAI合議自動承認」は異なります。実装開始時に設計文書を整合させます。msnc自体はどちらの承認方式でも同じ取得処理を使えます。

2. 一連の処理

1. 実行要求有効なmsnc配信元の期限を確認。source_idと実行時間枠からjob_keyを決め、実行履歴を作成。
2. 記事発見RSS/Atom・API・HTML一覧から記事URLを抽出。ドメイン許可、robots方針、件数上限を検証して取得待ちに保存。
3. 記事取得ホスト単位で順番に取得。HTTP条件付きリクエスト、タイムアウト、サイズ制限、リダイレクト再検証を適用。
4. 抽出・資料保存タイトル・本文・資料の公表日を抽出。原文、抽出本文、取得メタデータを非公開ストレージへ保存。
5. 判定待ち関連候補を永続的な待ち行列へ登録。既存の同一資料は再登録しない。選別理由も保持する。
6. msjd受け渡し保存済みsource_document_idで起動。記事中の指示は命令として扱わず、判定は資料から独立したルールで実行。

ニュース記事は通常、補助資料です。ニュースだけで一次資料確認済みにせず、必要な公式発表はmsicへ照会します。企業が曖昧、一次資料がない、モデルが不一致の場合はmsjdの保留・確認対象となります。

BeautifulSoupとの連携

Laravelが定期実行・安全なHTTP取得・DB保存を管理し、固定したPythonコマンドを引数配列で起動します。Pythonは外部通信・DB接続を行わず、取得済みHTMLと媒体コードを標準入力で受け取り、抽出結果を標準出力のJSONで返します。stdoutはJSON専用、診断はstderr。入力2MiB、抽出15秒、出力1MiBを初期上限として強制し、記事中の文字列をシェルコマンドや実行ファイル名に使いません。Python終了コード・JSON形式・必須項目を検証し、失敗時は抽出失敗として記録します。

初期のニュース候補はSecurity NEXT、ScanNetSecurity、ITmedia NEWSのセキュリティ記事。各媒体の取得・保存・AI送信条件とRSS提供状況を確認してから有効化し、記事内の公式発表リンクをmsicの追跡候補へ渡します。

候補選別

タイトルと本文の関連語（例：情報漏洩、不正アクセス、ランサムウェア、個人情報、事故、不祥事）を配信元別・版管理されたルールで評価。初期の取得対象期間は直近30日、候補は幅広く拾い、否定・過去事件への言及を単語だけで事実認定しません。非候補にも理由を残し、評価用サンプルから見逃しを測定します。将来の再評価に必要な本文は、確定した保管期限内だけ保持します。

3. テーブル案との対応と追加案

既存の18テーブル案を基礎にします。次の項目は実装計画で見つかった追加案であり、元のテーブル案へはまだ反映していません。name / base_urlのようなまとめ表記は、マイグレーションでは個別列へ展開します。

テーブル用途・追加内容制約・索引
crawl_sources既存：news、msnc、許可ホスト、schedule、extraction_config。追加：next_due_at、last_discovered_at、disabled_reason。scheduleにinterval_seconds、timezone、初回lookback_daysを保存。抽出設定にはadapter_code・版・許可パスを保持。(is_enabled, crawler_code, next_due_at)。設定JSONの形を検証。company_idをニュース媒体の記事対象企業として流用しない。
crawl_runs配信元の巡回単位。追加：discovery_finished_at、discovered_count、succeeded_count、unchanged_count、skipped_count、failed_count、heartbeat_at。statusにpartial、cancelledを追加案として定義。job_key UNIQUE。全記事の最終状態を集計して終了。記事失敗が残る実行をsucceededにしない。
crawl_items（新規）記事単位の取得待ちと再試行。id、crawl_run_id、source_id、normalized_url、url_hash、status、attempts、next_attempt_at、leased_until、lease_token、source_document_id NULL、error_code、discovered_at、finished_at。UNIQUE(crawl_run_id,url_hash)。status：queued / running / succeeded / unchanged / skipped / failed。索引(status,next_attempt_at)、(source_id,url_hash)。許可したURLのみ保存。
crawl_url_states（新規）URLごとの再取得状態。source_id、url_hash、normalized_url、etag、last_modified、last_checked_at、last_success_at、last_document_id NULL。巡回フィードにも同じ仕組みを利用。UNIQUE(source_id,url_hash)。304は既存資料への参照と確認時刻だけ更新。原資料がない304は条件を外して取り直す。
source_documents既存の資料スナップショットを保持。追加案：raw_sha256、raw_private_object_key、normalized_text_sha256、metadata JSONB。content_sha256は取得後の原文バイト列SHA-256に定義し、同一原文の重複保存を防ぐ。抽出版の違いは別途管理。既存UNIQUE(source_id,url_hash,content_sha256)を維持。titleや本文が抽出できない資料はAI候補にしない。原文保存の完了後にDB参照を確定。
document_processing_requests（新規）msjdへの永続的な受け渡し。id、source_document_id、extraction_version、selection_policy_version、selection_reason、status、attempts、next_attempt_at、leased_until、created_at。本文再抽出成果物の非公開キーも参照。UNIQUE(source_document_id,extraction_version,selection_policy_version)。status：pending / dispatched / acknowledged / skipped / failed。msjdが入力を永続化した時点でacknowledgedにする。

重複と更新

  • URLからフラグメントと既知の追跡パラメーターだけを除去。記事識別に必要なクエリは残す。末尾スラッシュやHTTP/HTTPSの同一視は配信元が保証する場合だけ行う。
  • canonicalリンクは許可ホスト・パスを検証して採用し、取得要求URL・最終URL・canonicalの対応はmetadataに残す。
  • 同じURLで原文が変化したら新資料行を作成。本文の正規化ハッシュが同じなら、広告等の変更だけでmsjdを再起動しない。
  • 転載・別媒体の記事は資料として個別保存。本文が似ていても同一インシデントと決めない。インシデントへの統合はmsjd/msadが根拠を確認する。
  • 原文不変の再抽出はsource_documentsを上書きせず、判定要求に抽出版と新しい成果物を保持。過去に使った抽出本文を追跡可能にする。

4. 取得・抽出の仕様

項目初期値・実装方針（提案）
頻度と負荷通常30分間隔、ホスト単位の同時接続1、最低取得間隔2秒。巡回1回あたり一覧100件まで。上限超過の続きは永続カーソルで次回処理し、未取得URLを消さない。
HTTP制限接続5秒、各リクエスト30秒、取得ジョブ全体90秒、リダイレクト3回まで。応答はストリームで読み、圧縮後・展開後とも2MiBを上限とする。バイト上限と時間上限は途中で強制終了する。
URL・SSRFHTTP/HTTPSの80/443のみ。資格情報付きURLを拒否。許可ホストを完全一致で比較。全A/AAAAを調べ、非公開・予約・ループバック・リンクローカル・メタデータ宛てを拒否。検証済みIPへ接続を固定し、Host/SNIと証明書検証はURLのホストを維持。IPv4写像IPv6も判定する。
リダイレクト・リンク自動追従を無効にし、各段階でURL、許可ホスト、DNS、robots方針を検証。RSSのURL、canonical、本文の公式リンクも同じ境界を通す。非許可の外部リンクを勝手に巡回しない。
robots・利用条件配信元ごとに利用条件・保存・AI送信の可否を記録。robots取得にも同じ通信制限を適用。取得不能時は初期方針として巡回を保留、Disallowは取得しない。robots許可を利用許諾と同一視しない。
本文抽出媒体別articleセレクターを優先。Laravelから取得済みHTMLを標準入力でPythonへ渡し、BeautifulSoupでscript/style/form/hidden・ナビ・広告を除去。PythonはJSONを返し、Laravelがスキーマを検証。最低本文長200文字を初期目安とし、短い正規発表は個別設定で許容。文字化け、ログイン画面、bot対策画面を取得成功の本文としない。
XMLRSS/Atomの外部エンティティとネットワーク参照を無効化。DOCTYPEを拒否。XMLサイズ、項目数、入れ子を制限し、XXE・大量展開を防止。
日付JSON-LDのdatePublished、媒体固有のtime、フィードの公表日時の順に出典を保存して採用。dateModified、HTTP Date、取得日時は公表日に代用しない。矛盾はNULLと警告。タイムゾーンが不明な時刻をUTCと決めつけない。
原資料保存公開用morashiter-site-prodと別の非公開バケット（仮称mrst-evidence-private）にraw/text/metaを保存。CDN閲覧キーに権限を付けない。msncは必要な領域への保存・参照権限だけ持つ。失敗時にDB参照だけ残さない。
保管の整合性原文ハッシュを含む不変キーへ保存し、整合確認後にDBトランザクションで資料・判定要求を登録。DB失敗後の孤立オブジェクトは一定猶予後に掃除。現役の根拠資料をTTLだけで削除しない。

5. ジョブ・再試行・運用

Schedulerは1分ごとに期限到来の配信元を探します。実際の巡回頻度は配信元設定から計算。DB行ロックとjob_keyの一意制約で同じ時間枠の多重登録を防ぎます。fileキャッシュのロックを複数コンテナ間の排他に使いません。

  • 記事待ち行列は期限付きleaseとlease_tokenで確保。古いワーカーはtokenが一致しない状態更新を行えない。停止したrunningは期限後に再投入。
  • 通信障害、408、429、5xxを最大3試行。待機は30秒・120秒を基準にジッターを付ける。429/503はRetry-Afterを尊重し、そのホスト全体を延期。期限はDBへ保存しワーカーをsleepで占有しない。
  • 401/403、404/410、robots禁止、SSRF拒否、本文不適合は通常の自動再試行対象にしない。403を回避するためにUser-Agentを偽装しない。
  • databaseキューのretry_afterを180秒、worker timeoutを120秒、ジョブ全体予算を90秒とする初期案。実装時に長い処理と衝突しないよう整合を確認。
  • msjd投入はDBコミット後に実行。ただしafterCommitだけに頼らず、pending/未acknowledgedの永続要求を定期的に再投入。受信側は要求IDで冪等に処理。
  • 配信元を無効化したら未開始の取得をcancelled/skippedにし、実行中は次の通信前に再確認。全体停止スイッチも設ける。

監視・ログ

source_id、run_id、item_id、HTTP状態、処理時間、受信バイト、結果分類を記録。本文、秘密キー、署名URL、認証ヘッダーはログに出さない。URLのクエリもログでは伏せる。連続失敗3巡回、成功取得が予定間隔の3倍以上ない、待ち行列の最古が2時間以上、容量不足を初期アラート条件にする。通知先は運用開始前に決める。

予定コマンド（実装後に利用）

php artisan msnc:discover --due
php artisan msnc:discover --source=SOURCE_ID --dry-run
php artisan msnc:retry --run=RUN_ID
php artisan msnc:status --source=SOURCE_ID
php artisan msnc:dispatch-pending
php artisan queue:work database --queue=msnc --timeout=120 --tries=1
php artisan schedule:work

--dry-runは登録設定の検証・対象表示だけを行い、外部通信・DB書き込みをしない。実接続検証用には別の--probeを設け、登録済み配信元だけを低頻度で取得する。記事の再試行回数はDB側で管理し、キュー側の無条件な再試行と二重化しない。

6. 実装順序と成果物

工程実装内容・予定ファイル完了条件
1. 契約・スキーマ取得対象設定と本文ハッシュの定義を確定。モデルCrawlSource/CrawlRun/SourceDocument、追加3テーブルのモデルとマイグレーション、msjd受け渡しDTOを作成。設計HTML/JSONも同期。新しいテストDBでFK・一意制約・statusのCHECK・索引を確認。現行DBを変更しない。
2. 通信境界app/Services/Crawling/UrlPolicy.php、SafeHttpFetcher、RobotsPolicy、HostRateLimiter。IP固定付き通信を集約し、アダプターから直接HTTPを呼ばせない。非許可宛て・リバインド・巨大応答・危険リダイレクトを拒否。
3. 発見・抽出app/Contracts/NewsSourceAdapter.php、RssAtomAdapter、媒体別HTMLアダプター、PythonArticleExtractor、Python側の媒体別BeautifulSoupアダプター、DocumentNormalizer、CandidateSelector。fixtureと抽出設定の版を保存。タイトル・本文・日付・URLを期待値と照合。抽出不能時に誤った本文を保存しない。
4. 永続取得app/Jobs/Msnc/DiscoverNews.php、FetchNewsArticle、app/Services/Crawling/DocumentStore.php。実行履歴、lease、条件付きGET、重複排除、更新版、部分失敗を実装。強制終了・重複配信・ストレージ/DB障害でも欠落を回復できる。
5. msjd接続DocumentProcessingRequest、DispatchDocumentProcessing、保留要求の再投入。初期受信先はmockで検証し、後にmsjdの実装へ接続。保存済み資料だけを渡す。再投入しても同一資料・設定の判定が増殖しない。
6. 定期運用Artisanコマンド、routes/console.php、config/msnc.php、schedulerサービス、msnc専用worker、運用手順。再起動復旧、停止スイッチ、失敗監視、秘密情報の扱いを確認。
7. 試験収集許可を確認した配信元を少数登録。公開パイプラインへ接続せず、1週間の収集と既知記事の捕捉率を測定。該当記事の見逃し・本文不良・更新追跡を評価し、媒体ごとの合格後に本運用へ。

工程1〜6をローカルfixtureで先に完成させ、工程7で実サイト固有の調整を行います。実装ブランチの提案はfeature/msnc-crawler。現在の設計ブランチを基点とし、今回の計画保存ではブランチは変更しません。

7. テスト・受入条件

  • RSS/Atom、相対URL、日本語エンコーディング、壊れたHTML、本文の短い記事、日付なし・矛盾した日付をfixtureで検証。
  • プライベートIPv4/IPv6、予約IP、URL認証情報、異なるポート、DNSリバインド、外部canonical、リダイレクト、XXE、圧縮爆弾を拒否。
  • 304、429とRetry-After、5xx、接続タイムアウト、robots取得失敗、認証画面、巨大応答、取得途中の停止を再現。
  • PostgreSQL実DBで同時実行・一意制約・lease競合を検証。SQLiteだけで競合制御の正しさを判断しない。
  • 同じURL・同じ原文は資料1件、原文更新は別版、本文不変の広告差分は追加AI判定なし。再抽出の版も追跡できる。
  • ストレージ保存後のDB障害、DBコミット直後のキュー障害、msjd投入直後のワーカー停止から未処理資料を回復。
  • 合格条件：代表fixture全件で必須抽出項目が期待値どおり、拒否すべき通信は全件拒否、再実行で重複判定なし、ログに本文・秘密情報なし。実媒体の捕捉率目標は既知記事の評価セットとともに運用前に決める。
