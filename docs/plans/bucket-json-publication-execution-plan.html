4. PR取り込み前の確認・補修とマージ

既存の生成・公開処理をそのまま活用する。以下はソース確認から判明した実施前の確認事項であり、本書では修正を実行していない。

4.1 事故本文を更新したときの識別子

現PRの version は merchants だけのハッシュなので、対応状況・出典など事故本文だけの更新では変わらない。拡張0.2.0には10分のキャッシュ期限と強制再確認があるが、本文更新も識別できるよう、配信対象の事故本文を含む決定的なデータからversionを生成する補修を公開前に行う。12桁の形式は維持し、生成時刻は含めない。

4.2 共有ドメインの扱い

現PRは登録ドメイン単位で複数ホストの会社名・事故IDをまとめる。異なる会社の店舗が同じ登録ドメインを共有する場合、登録済み店舗同士で事故情報を混ぜる可能性がある。初回登録は、1登録ドメイン＝1社と確認できる店舗に限定する。共有型ECの複数テナントを登録する場合は、先にホストごとの会社・事故対応へ分離し、そのテストを追加する。

4.3 公開確認と復旧の不足を埋める

  • ReleaseConfirmer が確認するのは release.json。公開履歴の live だけで成功とせず、メタと全256バケツを公開URLから読み戻す手順を追加する。
  • 旧リリースの再アップロードは、新たに置いたJSONを削除しない。初回導入時の復旧では、旧サイトの復元と api/v1 の取り下げを別々に扱う（第10節）。
  • 既存公開処理はスナップショットが同じなら skipped になる。ビルダー修正だけを反映する再公開の強制オプションは現在ない。必要になった場合はテストを先に追加して明示的な再公開手段を実装する。公開履歴を直接書き換えて回避しない。

補修を行う場合はPR #13を基に作業ブランチを作り、失敗するテスト → 実装 → 全体確認を行う。PR #13本体と補修をレビュー・マージし、実際にmainへ入った最終SHAをリリース対象にする。未マージのDraft SHAやGitHubの仮マージSHAを本番リリース番号として扱わない。

この段階の完了条件：最終コミットでPHP・静的サイト・拡張のテストが成功し、追加2マイグレーション、JSON契約、公開順序、復旧方針がレビュー可能になっている。

5. 実装前に準備するテストデータと検証

本番データで異常系を作らない。正常・異常・境界のfixtureを先に用意し、補修のテストが意図した理由で失敗することを確認してから実装する。

正常系

  • 架空会社A、承認済み事故1件、店舗ホスト2個。期待：両ホストで同じ事故、バッジ1。
  • 同一入力で2回生成。期待：同じJSON・version。
  • 公式出典がHTTPS。期待：拡張から一次情報を開ける。

更新・撤回

  • 事故のstatusまたはsourceだけを変更。期待：versionが変わり、再確認で新しい内容。
  • 店舗の無効化、事故の撤回。期待：対象の対応表・事故情報がバケツから消える。
  • 古いmeta＋新しいバケツ。期待：metaを1回取り直し、解消しなければ取得失敗。

異常系

  • 404、503、タイムアウト、不正JSON、異なるversion、存在しない事故ID。期待：「取得失敗」。
  • 公式出典がHTTPS以外。期待：公開前検証または拡張の検証で拒否。
  • アップロード途中失敗。期待：履歴failed、復旧対象にJSONも含む。

境界値

  • 登録店舗0件。期待：meta＋空のバケツ256個。サイト全体の事故0件とは区別する。
  • 同じ登録ドメインの未登録サブドメイン。期待：登録情報なし。
  • prefix長2・3・4、co.jp・lg.jp・IDN。期待：サーバーと拡張で同じ登録ドメイン・ハッシュ。
  • 別会社が同じ登録ドメインを共有。期待：今回の登録対象から除外、対応する場合は混在を防ぐテスト必須。

6.1 自動公開の登録

routes/console.php に Schedule::command('msgn:publish') を1件登録し、dailyAt('03:30')、timezone('Asia/Tokyo') を明示する。アプリ全体のUTC設定は変えない。MSGN_AUTO_PUBLISH と MSGN_ENABLED の両方が有効なときだけ実行する。スケジュールの重複防止と既存 SitePublisher の共有ロックを使い、手動公開との競合も防ぐ。定時処理はバックグラウンド実行し、他の収集・解析スケジュールを長時間止めない。

通常はschedulerコンテナを1つだけ起動する。ホストcronを代替に使う場合は、同じ新workerイメージ・共有アーカイブ・秘密設定で msgn:publish を毎日1回起動し、scheduler側の自動公開を無効にする。cronとschedulerの二重登録はしない。UTCのcronならJST 03:30は前日の18:30 UTC。cronのタイムゾーン対応を実環境で確認する。

8. 生成内容を確認してから、公開サイトに配置する

8.1 アップロードしない事前ビルド

Nodeが入ったmsncワーカーで php artisan msgn:snapshot --output=… を実行し、公開用スナップショットを専用の作業ディレクトリへ出力する。現在の release.json も取得して保存する。

ワーカーの /opt/site を作業ディレクトリにして、NodeSiteBuilder と同じ環境分離（env -i）で次を実行する。出力先は既存リリースや証跡を上書きしない専用ディレクトリとする。以下の <…> は実行前に確定する絶対パス。

node scripts/build-static.mjs --snapshot=<snapshot絶対パス> --previous-release=<現release.json絶対パス> --out=<新規dist絶対パス>
node scripts/verify-static.mjs <新規dist絶対パス> --snapshot=<snapshot絶対パス>

現在の MSGN_INDEXABLE=true を維持する場合は両方に --indexable を付ける。本番で --snapshot を省略しない。NodeプロセスへS3・DB・AIの秘密情報を継承させない。

  • meta＋256個のJSONがある。空バケツも生成されている。
  • 選んだ店舗ホスト・会社・事故ID・件数が期待どおり。未承認・撤回・無効ホストを含まない。
  • 本文と公式出典が管理画面の最新版と一致する。
  • サーバー生成JSONを拡張で読める。version・prefix・事故ID参照の整合が取れている。
  • 公開サイトの既存事故一覧・詳細・撤回表示を維持している。

8.2 初回リリースだけは手動公開で確認する

自動公開をまだ無効にした状態で、管理画面の /admin/publications から「公開実行」を1回押すか、新しいschedulerコンテナで php artisan msgn:publish を1回実行する。後者は通常運用と同じコンテナ・公開処理を確認できるため推奨する。CLIは同期実行であり、管理画面のジョブ投入と重複させない。初回の実データと公開URLを確認してから自動公開を有効にする。

処理順は、スナップショット → ビルド・検証 → 非公開アーカイブ → アセット → JSON → HTML → release.json → CDNキャッシュ削除 → release読み戻し。live を確認する。skipped の場合は実配置を確認し、未配置なら成功扱いしない。msgn:publish は公開無効時も終了コード0なので、終了コードだけで判定しない。

8.3 公開URLを読み戻す

  1. PCから通常のURLでmetaをGETし、HTTP 200、JSON、version、prefix_length=2 を確認する。クエリ付きでだけ成功する状態を完了としない。
  2. 全256バケツを順次または低い並列数でGETする。全て200、Content-Type: application/json、metaと同じversion、正しいprefix・参照・ハッシュ振り分けを確認する。保存した公開JSONは作業ディレクトリで検証し、失敗したファイルを記録する。
  3. metaの Cache-Control は public, max-age=300、バケツは public, max-age=600 を確認する。
  4. 実データ入りバケツと空バケツを少なくとも1つずつ直接開く。公開ページ、公式出典リンク、release.json のreleaseIdも確認する。

8.4 運用開始後：毎日03:30の自動生成・公開

  1. 日中にAI支援でインシデントDBを更新し、公開対象を人が審査・承認する。店舗ホストの確認も従来どおり行う。
  2. schedulerが毎日JST 03:30に php artisan msgn:publish を起動する。管理者が公開ボタンを押す必要はない。
  3. 変更があればスナップショットからサイトとバケツJSONを生成・検証・公開する。変更がなければ既存のハッシュ比較で skipped となり、再ビルド・アップロード・CDN削除を行わない。
  4. 実行結果の live または skipped と時刻を公開履歴に残す。公開ロックが使用中の busy、失敗、異常終了を成功扱いしない。
  5. Chromeは次の照合・キャッシュ更新で新JSONを読み込む。即時確認が必要なら「再確認」を使う。03:30以降に承認したデータは原則翌日の公開対象になる。

運用開始後に人が公開操作を行うのは、緊急の訂正・撤回・即時公開、障害復旧後の再実行だけとする。定時公開の失敗を放置して毎日ボタンで補う運用には戻さない。

8.5 scheduler / cron のログと監視

  • 毎日04:00 JSTを確認目安：03:30以降の site_releases に live または skipped があるか。実行自体がなければscheduler停止・設定無効・時刻設定・ロックを調べる。
  • コンテナ：schedulerの起動状態、再起動回数、終了コード、CPU・メモリ・ディスク、schedule:list の次回実行時刻とタイムゾーン。cron代替時はcronサービス状態とjournal/syslogの起動記録も見る。
  • 実行ログ：scheduler内 /app/storage/logs/msgn-schedule.log の開始・終了とコマンド出力（sendOutputTo で最新1実行分に上書きし、肥大化を防ぐ。過去の結果は site_releases とコンテナログで確認）、Laravelログの msgn: 失敗理由、Composeのschedulerログ。ログ領域の永続化・容量・ローテーションも確認する。
  • 公開結果：building/built/uploaded が長時間残る、failed、busy、S3/CDN失敗、release読み戻し失敗を調べる。前日の live だけでは当日の正常実行を証明しない。
  • 外形監視：metaと実データ入りバケツの200、JSON形式、version整合、対象事故ID、公開releaseを確認する。skipped で日付やversionが変わらないのは正常であり、「versionが変わらない」だけで異常にしない。
  • 障害対応：ログと設定を確認し原因を修正後、同じコマンドを手動で1回再実行する。重複実行中でないことを確認してから行う。ロックを根拠なく削除しない。

既存監視サービスがある場合は「04:00時点で当日正常実行なし」「公開failed」「外形JSON不整合」を登録する。通知先が未設定なら、監視登録は未完了として明示する。新しい通知先への送信を暗黙に開始しない。

10. 問題が出たときの止め方と戻し方

metaが404
公開が実行されたか、ワーカーが新イメージか、対象S3・CDNパス、公開履歴のfailed/skippedを確認する。店舗未登録でも本来metaと空バケツは生成されるので、「登録がないから404」と扱わない。
metaは200だが店舗が出ない
正確なホスト名、会社関連付け、承認・撤回状態、ホスト無効化、スナップショットの merchants、該当バケツを順に確認する。
バケツとmetaのversionが違う
公開完了・CDN削除を待ち、再確認する。拡張は1回だけmetaを取り直す。繰り返し不整合になる場合は取得失敗のまま止め、再公開前に原因を確認する。
誤った会社・事故が表示された
対象ホストを無効化し、新バージョンの公開処理が正常なら直ちに再公開する。関係する事故と他店舗の影響を確認し、訂正後に再登録する。
アプリ更新を戻す必要がある
保存したweb・workerの両digestへ戻し、対象コンテナを再作成する。追加テーブル・nullable列は原則保持し、migrate:rollback やDB全復元を自動で行わない。
旧サイト復元だけでは新JSONが残る。現在の復旧処理は前回アーカイブを再アップロードする方式で、旧アーカイブにない api/v1 の新オブジェクトを削除しない。また MSGN_ENABLED=false は次回公開を止めるだけで、公開中のJSONは消えない。

公開前に、メタと全256バケツを復元対象として保存する。導入前にAPIが存在しない場合は「存在しなかった」ことと追加予定257キーを記録する。障害時は運用担当がこの限定リストに基づいて旧JSONを復元、または新規257キーだけを取り下げ、CDNキャッシュを削除する。サイト全体や証跡バケットを再帰削除しない。

JSONを取り下げても拡張に既存キャッシュが残る。手動の「再確認」で即時に取得失敗へ切り替わることを確認し、通常の結果は次の照合時の10分TTL更新まで残り得ることを記録する。復旧後も release.json とJSONをそれぞれ外部から読み戻す。
