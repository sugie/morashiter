1. 位置づけ

実装計画書の 6 章（ルートと API）と 7 章（DB）を、管理画面モックで追加した次の 3 つに合わせて詳しくしたものです。赤字は実装計画書にない追加です。

  • PayPal 案内の条件：カード情報またはアカウント情報の公表事実があり、その店舗で PayPal が使えると確認済みのときだけ、拡張に選択肢を出す。
  • 店舗ごとの PayPal 対応：根拠 URL つきで管理者が登録する。
  • 案内の流れの集計：デモ店舗のサーバー側だけで数える。拡張は閲覧データを送らない。

既存の表（incidents、incident_revisions、companies、official_domains、site_releases、admin_users）は 2026-11-02 時点の services/mrst/database/migrations を読んで確認しました。

2. 方針

  • 照合は拡張の中で行う。ホスト名を受け取る API は作らない。拡張は対応表（静的 JSON）を丸ごと取得し、手元で照合する。閲覧中の URL はどこにも送らない。
  • 案内を出すかどうかはサーバーが決める。条件の判定は対応表を作るとき（PHP）に 1 か所で行い、結果を paypal_option として対応表に入れる。拡張はそれを表示するだけにする。判定のテストを PHP 側にまとめられ、拡張と条件がずれない。
  • 追加だけ。既存表への変更は nullable 列の追加 2 つ（incidents.company_id、incident_revisions.data_categories）。旧コードのままでも動く。
  • 管理画面は既存と同じ Blade とセッション。管理用の JSON API は作らない。すべて /admin（既存の IP 制限とログイン）の中に置く。
  • 個人の情報を持たない。デモ店舗の集計にも IP アドレス・User-Agent・購入者の情報・PayPal の応答本文を保存しない。

3. 全体の流れ

[公開時: mrst-prod-msnc]
  merchant_domains × companies × incidents(承認・未撤回) × merchant_payment_options
    └→ MerchantIndexBuilder → api/v1/merchant-index.json（S3/CDN、静的）

[利用者の Chrome]
  拡張: 対応表を取得（ETag で更新確認）→ タブのホストを手元で照合 → バッジとパネル
    paypal_option があれば「支払いの選択肢」を表示
    └→ リンク先（デモ店舗のときだけ ?via=morashiter-ext を付ける）

[api.morashiter.com: mrst-prod-app]
  /demo-shop?via=morashiter-ext   → demo_visits に 1 行（Cookie の乱数 ID のみ）
  POST /api/v1/demo/orders        → demo_orders（押した）→ PayPal 注文作成
  PayPal で承認／キャンセル
  POST .../capture または .../cancel → demo_order_events に記録
  /admin/paypal/guidance          → 上の 3 表から集計して表示

5. 公開 API の詳細

5.1 merchant-index.v1（拡張が読む対応表）

{
  "schema_version": "merchant-index.v1",
  "scope": "production",                 // デモは "demo"
  "release_id": "a1b2c3d4e5f6",
  "data_as_of": "2026-10-25",
  "domains": {
    "shop.northwind-goods.example": {
      "company": "Northwind Goods (fictional)",
      "incident_ids": ["INC-021"],
      "paypal_option": {                 // 条件を満たすときだけ入る。満たさなければキー自体がない
        "incident_ids": ["INC-021"],     // 条件を満たした公表事実
        "link": "https://shop.northwind-goods.example/help/payment",
        "evidence_url": "https://shop.northwind-goods.example/help/payment",
        "checked_at": "2026-11-05"
      }
    }
  },
  "incidents": {
    "INC-021": { "id": "INC-021", "name": "…", "company": "…", "type": "…", "date": "2026/10/20",
                 "disclosure": "漏えい確認", "quantity": "…", "dataType": "…",
                 "dataCategories": ["card", "contact"],   // 追加。未設定は []
                 "status": "…", "source": "https://…", "contact": "https://…" }
  },
  "withdrawals": [ { "id": "INC-017", "date": "2026/11/01", "reason": "…" } ]
}

paypal_option を入れる条件（PaypalGuidancePolicy、すべて満たすとき）

  1. ドメインが有効（merchant_domains.disabled_at が null）。
  2. そのドメインに merchant_payment_options（method = paypal, status = confirmed）がある。
  3. その会社に、承認済み・未撤回で、最新版の data_categories に card か account を含むインシデントが 1 件以上ある。

撤回したインシデント、data_categories が未設定（null）のインシデントは条件に数えない。対応表に載らないホスト（拡張では「登録情報なし」）、取得失敗、対象外のページには、拡張は何も出さない。

link は、デモ店舗なら https://api.morashiter.com/demo-shop?via=morashiter-ext。実在の店舗には到着を数える手段がないため、店舗自身の支払い方法のページ（根拠と同じ URL）を指し、印は付けない。

5.2 デモ店舗への到着

GET /demo-shop?via=morashiter-ext
  - Cookie demo_visit（UUID v4、Path=/demo-shop と /api/v1/demo、HttpOnly、Secure、SameSite=Lax、7 日）がなければ発行
  - demo_visits に (id, via) を 1 回だけ記録（同じ Cookie の再訪は増やさない）
  - via は "morashiter-ext" と "direct" の 2 値だけ。それ以外の値は "direct" として扱う

5.3 注文作成（「PayPal で支払う」を押したとき）

POST /api/v1/demo/orders
{ "product_id": "nw-mug-01", "client_request_id": "uuid-v4" }   // 金額は受け取らない。未知のキーは 422

201 { "orderId": "5O190127TN364715T" }    // v6 の createOrder がそのまま返せる形
  1. client_request_id で demo_orders を探す。あれば同じ orderId を返す（再送で増えない）。
  2. なければ status = requested で行を作る（ここが「押した」の記録）。visit_id は Cookie から。
  3. PayPal POST /v2/checkout/orders（PayPal-Request-Id = client_request_id、金額はカタログ）。
  4. 成功：paypal_order_id を保存、status = created。失敗：status = failed、error_code。
HTTPcode場合
422invalid_input未知の商品、UUID でない、未知のキー
429rate_limited20 回／分／IP を超えた
502paypal_unavailablePayPal の 4xx・5xx・タイムアウト
404—DEMO_SHOP_ENABLED=false

5.4 capture（PayPal で承認したあと）

POST /api/v1/demo/orders/{orderId}/capture      // 本文なし

200 { "status": "COMPLETED", "amount": "12.00", "currency": "USD", "product_id": "nw-mug-01" }
  1. demo_orders を paypal_order_id で行ロック（SELECT … FOR UPDATE）。イベント capture_requested。
  2. 行がない、または visit_id が Cookie と違う → 409 not_your_order。
  3. すでに captured → イベント capture_duplicate_blocked を記録し、保存済みの検証結果を 200 で返す（PayPal は呼ばない）。
  4. PayPal GET /v2/checkout/orders/{id}：状態 APPROVED、金額・通貨がカタログと一致を確認。違えば 422 verification_failed（イベント verification_failed）。
  5. PayPal POST …/capture（PayPal-Request-Id = capture_request_id、行に固定した UUID）。
  6. capture の status が COMPLETED、金額・通貨が一致 → status = captured、verification に 4 項目を保存、イベント captured。

5.5 キャンセル（新規）

POST /api/v1/demo/orders/{orderId}/cancel      // JS SDK の onCancel から呼ぶ。本文なし
204

created の注文だけを cancelled にし、イベント cancelled を記録する。captured の注文には何もしない（409 already_captured）。PayPal 側の操作はしない（承認されていない注文は自然に失効する）。

8. 案内の流れの集計（/admin/paypal/guidance）

期間は demo_visits.created_at が直近 N 日のもの。数えるのは via = morashiter-ext の到着から始まった注文だけ。

段画面の表示数え方
1拡張から店舗を開いたdemo_visits（via = morashiter-ext）の行数
2「PayPal で支払う」を押したその visit に紐づく demo_orders の行数
3注文を作成2 のうち paypal_order_id が null でないもの
4PayPal で承認3 のうち capture_requested イベントがあるもの（承認すると JS SDK が capture を呼ぶため）。キャンセル = status cancelled
5capture・検証済みstatus captured かつ verification の 4 項目がすべて true。二重 capture の阻止 = capture_duplicate_blocked イベントの数

割合は前の段に対する比で、分母が 0 のときは「—」。集計は都度 SQL で行う（デモの規模では集計表は不要）。

11. 未決事項（判断をお願いしたいもの）

  1. モックの表示例と条件のずれ（2026-11-02 解決）。PayPal 案内の画面の表示例を、決済画面の改ざんでカード番号・有効期限・セキュリティコードが盗まれた可能性という事実（区分 card）に直した。条件は card と account のままとする。
  2. 拡張の権限。現在の MVP（extensions/chrome/、未 push）は自動でバッジを出すため tabs を使っています。計画書は activeTab（アイコンを押したときだけ）です。どちらでも本 API は同じですが、審査員への説明とプライバシーの書き方が変わります。
  3. 実在の店舗の PayPal 対応を載せるか。載せる場合、根拠ページの確認は人が行い、定期的に見直す必要があります。デモでは架空のデモ店舗だけにする案もあります。
  4. data_categories の既存分。既存の承認済みインシデントに区分を付けるかどうか（付けない限り、それらには案内が出ません）。
