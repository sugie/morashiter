1. 課題

ダッシュボードの「公式発表が見つからない」は 15 件あり、審査キューに進まない最大の原因になっている（2026-11-06 時点）。ニュース記事が企業のトップページにしかリンクしていないため、個別の発表にたどり着けていない。

今は、管理者が1件ずつ公式サイトを探し、URL を手で貼っている。1件あたり数分かかり、件数が増えると回らない。

目標：管理者の作業を「AI が見つけた候補を開いて確かめ、1回押す」だけにする。追加・承認・公開を自動で行うことはしない（人の確認は残す）。

2. 今の仕組み（コードで確認）

  • FetchOfficialSource がトップページを1枚取得し、OfficialPageLinkFinder が同じホストのリンクの中から、リンクの文字に「不正アクセス・漏えい・流出・お詫び…」を含むものを最大3件拾う。1件も無ければ no_incident_link で終わる。
  • 見逃す原因：
    • 発表が「お知らせ一覧」「ニュースリリース」「IR」などの2階層目以降にある
    • 見出しに上の語が無い（「当社サービスに関するお知らせ」「重要なお知らせ」など）
    • 発表が PDF だけ
    • トップページが JavaScript で描画されている
  • 流用できる部品：
    • SafeHttpFetcher・UrlPolicy・HostResolver：取得の安全策（https、公開 IP、リダイレクト検証）
    • HostRateLimiter：ホストごとの間隔
    • OfficialDomainPageCollector：同じホスト内の巡回（今は最大3ページ）
    • SakuraDomainResearcher：さくら AI に、取得したページだけを根拠として判断させ、引用が本文に実在するかをコードで確かめる方式
    • AiUsageBudget：1日の上限
    • ManualOfficialAnnouncement：手動追加の登録と取得ジョブの投入

3. 方針

  • 探す範囲は、登録済みの公式ホストの中だけ（外部の検索エンジンや他サイトは使わない）。根拠は「その組織自身が公表したもの」に限る、という今の原則を守る。
  • まずルールで候補を集め、AI には「どれが同じ事件か」の判断だけをさせる。AI に URL を考えさせない（作り話の URL を防ぐ）。
  • AI の出力はコードで検証する：
    • 候補の URL は、集めた一覧にあるものだけを受け付ける。
    • 引用は、取得した本文に実在するものだけを受け付ける。
  • 最後は人が押す：AI の候補は「おすすめ」として表示するだけにする。追加ボタンを押すまで、何も登録しない。

5. 推奨案（B）の流れ

[対象] official_link_candidates のうち status=fetched かつ error_code=no_incident_link
       （または、取得に失敗して管理者が「AIで探す」を押した候補）

1. 予約
   - 「AIで探す」ボタン、または毎時の自動予約（1日の上限内）
   - official_announcement_searches に queued で1行
2. 候補URLを集める（ルール。同じホストだけ。最大 10 ページ・合計 5MB・ホストごとの間隔を守る）
   a. robots.txt の Sitemap 行 → sitemap.xml（入れ子は 2 段まで）
   b. トップページの <link rel="alternate"> にある RSS/Atom
   c. トップページから、文字が「お知らせ|ニュース|新着|プレス|IR|重要|情報公開」の同じホスト内リンク（一覧ページ）を 3 枚まで
   d. a〜c から、同じホストの記事・PDF の URL・見出し・日付を集める
3. 絞り込み（ルール、AIなし）
   - 日付：元ニュースの公開日の前 30 日〜後 7 日（日付が無いものは残す）
   - 点数：
     - 見出しに事件の語がある：＋
     - 見出しに元ニュースの題名の語がある：＋
     - PDF：＋
     - 方針・規約のページ：除外
   - 上位 15 件
4. AI で照合（さくら AI、既存の方式）
   - 入力1：元ニュースの題名・公開日・組織名（ニュース本文は入れない）
   - 入力2：上位 15 件の見出しと URL
   - 出力：候補番号（最大 3 件）と理由。※URL は書かせず、番号で答えさせる
5. 本文で確認（上位 3 件を取得して、AI に再確認）
   - 「元ニュースと同じ事件の公表か」を yes/no/unclear で判定し、本文からの引用（最大 2 つ）を付けさせる
   - コードで確認：引用が本文に実在すること、URL が集めた一覧にあること、ホストが一致すること
6. 結果を保存
   - completed：proposals に、URL・見出し・日付・判定・引用・順位
   - 失敗：failed（理由コード）
7. 人が確認（6章の画面）
   - 管理者が候補を開いて「この URL で追加」を押す
   - → 既存の ManualOfficialAnnouncement で登録して取得へ（この先は今と同じ）

手順2〜3だけ（案A）でも価値がある。AI を止めた状態（ANNOUNCEMENT_SEARCH_AI=false）でも、ルールの候補一覧は表示する。

6. 画面の変更（/admin/official-announcements）

  • 「公式発表を見つけられなかった候補」の各行に、状態と操作を付ける。
    • 状態：AI探索（未実行／探索中／候補あり／見つからず／失敗）
    • 操作：「AIで探す」（再探索も同じボタン）
  • 候補ありの行では、候補を最大3件表示する。各候補に出すもの：
    • 見出し・日付・URL（新しいタブで開く）
    • AI の判定（同じ事件／不明）
    • 本文からの引用
    • 「この URL で追加」ボタン
  • 「この URL で追加」：
    • 組織とドメイン・URL を入れた状態で、既存の追加フォームへ移る（または同じ画面で送信する）。
    • 「発表本文を開いて確認しました」のチェックは、これまでどおり必須にする。
  • 「どれも違う」ボタン：理由を残して、その探索を閉じる。同じ候補を自動で再探索しない（手動の再探索は可能）。
  • 表示の注意書き：「AI の候補は未確認です。本文を開いて、同じ事件の組織自身の発表であることを確かめてから追加してください。」
  • ダッシュボードの「公式発表が見つからない」カードに、「AI 候補あり n 件」を足す。

8. 安全策

  • 取得：既存の SafeHttpFetcher と UrlPolicy を使う。
    • https のみ
    • 登録済みホストと完全一致
    • 公開 IP への名前解決
    • リダイレクトは同じホスト内だけ
    • サイズとタイムアウトに上限
    • ホストごとの間隔
    • 本番の User-Agent
    • robots.txt の Disallow を守る
  • プロンプトインジェクション：取得したページの文章は、すべて「信頼しないデータ」として区切って渡す（既存の方式と同じ）。AI が返してよいのは「候補番号・判定・引用」だけにする。指示文に従った出力（番号以外の URL、知らない番号、本文に無い引用）は捨てる。
  • 作り話の防止：
    • AI に URL を書かせない（番号で選ばせる）。
    • 引用は、本文に文字どおり含まれるかをコードで確かめる。
  • 自動化の範囲：
    • 探索と候補の表示まで。
    • 追加は人がボタンを押したときだけ。承認と公開は、今までどおり別の操作。
  • 記録：ログには候補 ID・状態・ページ数だけを残す。ページの本文や AI の生の応答はログに出さない（DB には検証済みの引用だけを保存する）。
  • 費用の上限：
    • 1日の上限は、公式発表の解析とは別に持つ。
    • 上限に達したら、ルールの候補だけを表示する。

9. 設定と費用

ANNOUNCEMENT_SEARCH_ENABLED=false     # 機能全体（false で画面のボタンも出さない）
ANNOUNCEMENT_SEARCH_AI=true           # false ならルールの候補だけ（案A）
ANNOUNCEMENT_SEARCH_AUTO=false        # true で no_incident_link の候補を毎時自動予約
ANNOUNCEMENT_SEARCH_MAX_PER_DAY=20    # AI 探索の1日の上限（AI_MAX_ANALYSES_PER_DAY とは別）
ANNOUNCEMENT_SEARCH_MAX_PAGES=10      # 1件あたりの取得ページ数の上限

AI の呼び出しは1件あたり最大4回（照合1回＋本文確認3回）。15件の滞留を一度に処理しても約60回で、さくら AI の既存の上限内に収まる見込み（実際の単価は実装時に ai:check で確認する）。

10. テスト（TDD。先に書くもの）

CI の fixture-news（nginx）に、架空の公式サイトを置く。

  • トップページ
  • robots.txt と sitemap.xml
  • お知らせ一覧
  • 「当社サービスに関するお知らせ」（見出しに事件の語が無い発表）
  • 発表 PDF
  • 指示文を埋め込んだページ
  • 別ホストへのリダイレクト
外部のサイトにはつながない。AI は HTTP をモックする。

対象正常異常・境界
候補の収集（ルール）sitemap・RSS・一覧ページから、同じホストの記事と PDF を集める。日付で絞って点数順に並べる
  • sitemap が無い
  • sitemap が入れ子3段（2段で止める）
  • robots の Disallow
  • 別ホストへのリダイレクトと別ホストのリンクは除外
  • 上限の10ページで止まる
  • 方針・規約のページは除外
  • 日付が無いものは残す
AI 照合番号で選んだ候補と引用が保存される
  • 知らない番号
  • URL を直接書いた出力
  • 本文に無い引用
  • JSON の不正
  • 429・5xx・タイムアウト
  • 上限に到達したらルールの候補だけ
  • 指示文入りのページでも出力の形式が守られる
画面候補・引用・「この URL で追加」が出る。押すと既存の手動追加を通って取得が始まり、suggested_by_search_id が記録される
  • チェックが無ければ追加しない
  • 「どれも違う」で閉じる
  • 二重の予約は1つになる
  • 無効な管理者と許可外の IP は拒否
  • 引用は HTML エスケープされる
  • 機能フラグ off ならボタンが出ない

実行は bash bin/mrst-ci-test.bash と GitHub Actions の mrst-phpunit。本番の AI と実在サイトでの確認は、フラグを on にした後に人が行う。

12. 判断をお願いしたいこと

  1. 進め方：段階1（ルールのみ）から始めてよいか。AI（段階2）まで一度に作るか。
  2. 時期：ハッカソン提出（11/12）の前に入れるか、後にするか。
  3. 自動予約：「AIで探す」をボタンだけにするか、毎時自動で回すか（費用は9章の上限内）。
  4. Web 検索 API（案C）：今回は使わない方針でよいか。
  5. 一緒に直すか：同じ画面の「選択肢に公式ドメインがない場合」の企業名欄も、選択欄（AI 調査・候補・その他）に揃えるか。
