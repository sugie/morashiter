# 検証計画

## 検証する仮説

| ID | 仮説 | 反証条件 | 検証方法 |
|---|---|---|---|
| H1 | 被害者は対象確認と次の行動に迷う | 8割以上が企業通知だけで十分に行動できる | 被害経験者10〜15人へのインタビュー |
| H2 | 支援主体は受付・証拠整理に大きな事務負担を抱える | 構造化受付が実務時間をほぼ削減しない | 弁護士3〜5人、団体2〜4組織へのインタビュー |
| H3 | 法律判断を行わない受付基盤として成立できる | 中核機能が法律事務・周旋なしには成立しない | 個人情報・消費者法・弁護士法のレビュー |
| H4 | 高機密原本を中央保管せずに価値を出せる | 支援主体が原本の事前集中保管を必須とする | ローカルファースト試作の評価 |
| H5 | 無料救済導線と有料の平時機能を分離できる | 有料機能に継続利用意向がない | 価格インタビュー、課金モック |
| H6 | 単独事件から横展開できる | 事件ごとに必要項目が違いすぎて共通化できない | 3種類以上の過去事案でデータモデルを検証 |

## 対象者

### 被害経験者

- 企業から漏えい通知を受け取ったことがある
- 実害あり・なしを分ける
- 現役会員・退会者を分ける

募集時に、氏名、企業名、会員番号、免許証画像などの提出を求めない。

### 専門家・団体

- 個人情報漏えい事件を扱った弁護士
- 消費者事件を扱う弁護士
- 特定適格消費者団体の被害回復業務担当
- 消費生活相談員
- セキュリティ／プライバシーエンジニア

## 実施順

1. 支援主体3者へ問題インタビュー
2. 被害経験者5人へ問題インタビュー
3. 紙またはクリック可能モック作成
4. 被害経験者5〜10人へタスクテスト
5. 支援主体へケース概要の出力形式を評価してもらう
6. 法務・セキュリティレビュー

解決案を先に説明せず、現在の行動・負担・失敗を聞いてからモックを見せる。

タスクテストは [被害経験者向けユーザビリティテスト手順](./usability-test-protocol.md) に従う。試作内の検証モードから書き出すデータには、対象確認の回答内容、証拠チェックの内訳、端末内メモ、意思表示の内訳を含めない。

被害経験者テストは5人、別の5人、UI固定後の別の10人の合計20人で行い、各段階を[Gate B判定キット](./gate-b-scorecard.md)で判定する。異なるUIバージョンの成績を合算しない。

支援主体による出力形式の評価は [支援主体向け評価セッション手順](./support-evaluation-protocol.md) に従う。実在案件を使用せず、架空サンプル5件と閉じた選択肢の評価票でGate Aを判定する。

## 記録テンプレート

各セッションで以下を記録する。

- 匿名ID
- 対象者区分
- 実施日、所要時間
- 現在の行動フロー
- 最も大きい負担
- 現在使っている代替手段
- 発言事実と観察者の解釈を分離したメモ
- 仮説を支持／反証する証拠
- 次に確認すべき点

録音は原則しない。必要な場合は目的、保存期間、閲覧者、削除日を説明し、明示同意を得る。

## 判定

各仮説を `支持 / 一部支持 / 反証 / 未確認` で管理する。「興味がある」「使ってみたい」だけでは支持としない。現在の行動、実際の時間、具体的な提供意思を強い証拠とする。
