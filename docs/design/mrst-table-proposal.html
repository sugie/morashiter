msncはニュース記事、msucは企業公式発表を取得。msjdは保存済み資料を複数モデルへ渡して合議し、msadは不一致・訂正・募集情報を管理します。API①は希望ボタン・購読・統計を担当します。

今回の設計判断

  • 企業とサービス名を区別し、一件のインシデントに複数企業を関連付けます。
  • インシデントの識別、内容の版、AI承認、配信成功を分離します。続報・訂正で古い根拠を上書きしません。
  • 発生日、初回公表日、参照資料の公表日、取得日時を区別。日付不明を0や推定日で埋めません。
  • 件数は数値・単位・対象範囲・概数表現を保持。重大度は未算定を許容し、ランキング基準は別途確定します。
  • 全必須モデルの成功と重要項目の一致、一次資料の裏付けを条件に自動承認。既存crawler-and-ai.mdの全件人手承認方針とは異なる今回の提案です。
  • 暗号化メールとHMACによる検索キーを分離。個人情報・証拠資料は静的サイト配信対象から除外します。

制約・索引・運用の共通方針

  • 内部IDはbigint、公開用IDはuuid、処理日時はtimestamptz、資料上の日付はdate。全外部キー列に必要な索引を作成します。
  • status等はCHECK制約で許可値を限定。任意文字列のまま本番導入しません。数値は非負・スコアは0–100。
  • 主要索引：incident_revisions(incident_id, revision_number)、(status, source_published_on)、source_documents(source_id, fetched_at)、ai_judgment_runs(revision_id, started_at)、publication_jobs(status, requested_at)、各購読・希望テーブルのincident_id。
  • 外部キー削除は原則RESTRICT。監査・一次資料・公開版を連鎖削除しません。トークンなど子データの削除は保持方針を決めて実装します。
  • 書き込み・登録直後の統計はMainへ接続。ReplicaはSSGの許容遅延が明確な読み取りだけ。初期SSGはMainで版を固定します。
  • DBロールはアプリごとに必要な表だけ許可。公開APIから資料本文・判定生ログ・管理者表を読めないようにします。PgBouncer経由でもトランザクション単位の整合性を維持します。
  • 認証メール・通知メールの配信履歴とLaravelのjobs/failed_jobs、セッション、キャッシュ表はインフラ方式決定後の追加対象。業務表18件に含めていません。

実装前に確定する項目

  1. AIモデル2種と確度閾値、重要事実の一致ルール。90は初期案であり評価用データによる検証が必要。
  2. 漏えい以外の不祥事種別、対応状況コード、重大度の計算基準。
  3. 希望ボタンのHMAC対象・保持期間・鍵ローテーション方法。
  4. 購読メールと証拠資料・AI生ログの保存期間、解除・削除方針。
  5. メール送信基盤と再送・通知の重複防止、管理者認証・MFA。
  6. ビルド失敗時の公開版復旧手順、撤回時のCDNキャッシュ更新保証。
