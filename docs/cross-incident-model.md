# 事件横断データモデルの一次検証

調査日: 2026-09-30  
対象: タイムズカー2026、JINSオンラインショップ2017、LINEヤフー2023–2024  
結論: **H6は一部支持。共通層は作れるが、対象条件の質問を共通固定項目にしてはいけない。**

これは各企業の公式発表を比較した机上検証であり、漏えい事実・責任・請求権に関する独立認定ではない。

## 公式発表の比較

| 観点 | タイムズカー | JINS | LINEヤフー | 設計への示唆 |
|---|---|---|---|---|
| 公表時の状態 | 第2報で第三者取得を確認、第3報で本人確認書類約160万件を追記 | 当初は「アクセスできる状況」、最終報告で漏えい確認 | 漏えいと可能性を併記し、複数回更新して最終調査 | `possible / confirmed / final` を混ぜず、発表版ごとに保持 |
| 対象者の関係 | 現会員、退会者、入会未完了、法人サービス会員 | オンラインショップ顧客 | ユーザー、取引先、従業者等。既存・退会ユーザーも通知対象 | `membership` 一項目では表現できない。事件別の関係区分が必要 |
| 件数の単位 | アカウント数 | 顧客情報件数 | 個人データ件数、推計値、アカウント数を混在 | 人数と件数を同一視しない。単位・概数・推計含有を持つ |
| 情報カテゴリ | 連絡先、免許情報、本人確認書類画像、ハッシュ化パスワード等 | 連絡先・属性。カード情報は非漏えい確認 | 内部識別子、利用履歴、通信の秘密関連、取引先・従業者情報等 | 事件側の公開カテゴリと、個人ごとの確認状態を分離 |
| 個別通知 | 本人確認書類漏えい確認者へ個別案内開始 | 流出確認者へ個別連絡予定 | リスク評価・連絡可能性に応じ個別連絡。連絡不能者は公表を通知とする | 「通知未受領＝対象外」と判定してはいけない |
| 推奨行動 | なりすまし・フィッシング注意 | 不審メール注意 | フィッシング注意。対応不要とした対象もある | 推奨行動は事件版ごとに一次情報から生成し、共通断定しない |

## 現行v1の限界

現在の最小共有パケットはタイムズカー用に、`answers.membership` と `answers.notice` を固定している。この二つはタイムズカーでは有用だが、次の問題がある。

1. JINSの「オンライン購入者」と一般的な会員関係を同一視する
2. LINEヤフーのユーザー、取引先、従業者を表現できない
3. 個別通知を受け取れない対象者を、対象外へ誤って分類する危険がある
4. アカウント数、顧客情報件数、個人データ件数を同じ人数として集計しかねない
5. 公表が「可能性」から「確認」へ更新されたとき、同じルール版のまま評価が変わり得る

したがって、v1を別事件へ名前だけ置き換えて再利用しない。

## v2の三層構造

### 1. 公開事件カタログ

サーバー保存できる公開情報。利用者回答を含めない。

- `incidentId`: 内部で安定した事件ID
- `displayName`: 表示名
- `publisher`: 発表主体
- `sourceSnapshots[]`: URL、発表日、確認日、資料版
- `publicationStatus`: `preliminary / updated / final / unknown`
- `affectedCount`: 値または範囲、`unit`、概数か、推計を含むか
- `audienceScopes[]`: 消費者、退会者、申込者、取引先、従業者等
- `publicDataCategories[]`: 公式発表上の情報カテゴリ
- `notificationPolicy`: 個別通知の範囲と、未通知が意味すること
- `recommendedActions[]`: 一次情報に明記された一般的行動
- `unknowns[]`: 個人ごとの漏えい項目、責任、補償等の未確認事項

### 2. 事件別アダプター

端末内で実行する、版付きの質問と規則。事件ごとに許可値を固定する。

- `adapterVersion`
- `questions[]`: 質問ID、選択肢、`unknown` の許可
- `normalization`: 事件固有回答を共通区分へ写像
- `assessmentRules`: 公表条件上の `possible / unclear / unlikely`
- `allowedEvidenceKinds[]`
- `explanations`: 判定理由、判定できないこと

生成AIの自由回答で対象判定しない。発表更新時は既存アダプターを上書きせず、新版を追加する。

### 3. 最小共有パケット

支援主体へ渡す候補。事件固有の生回答ではなく、必要最小限の正規化結果を中心にする。

- `incidentId`
- `adapterVersion`
- `assessment`
- `relationshipCategory`: `current-user / former-user / applicant / purchaser / business-contact / workforce / unknown / other`
- `notificationStatus`: `direct-received / not-received / public-only / unknown`
- `evidenceHeld[]`: 原本ではなく保有種類
- `impactSignals[]`: `none-known / suspicious-contact / account-misuse / payment-fraud / expense / time-cost / other` の粗い区分
- `intent`
- `consentBoundary`

`workforce` や `business-contact` は事件カタログの完全性のための区分であり、RightsRelayが労働事件・企業間紛争を扱うことを意味しない。対象外領域は適切な窓口を表示し、消費者被害の集計へ混ぜない。

## 重要な不変条件

- 個別通知の未受領だけで対象外にしない
- 事件の公開情報カテゴリを「その個人について漏えいした情報」と表示しない
- `accounts / records / persons / estimated` を変換せず保持する
- 同じ `incidentId` でも `adapterVersion` が異なるパケットを無注記で合算しない
- 対象可能性と請求権・制度対象を分離する
- 事件別アダプターが許可しない質問・回答キーを拒否する
- 自由記述、原本、正確な被害額を初期共有パケットへ入れない

## 移行判断

現行試作はタイムズカー専用v1として維持する。次の条件を満たすまでv2へ移行しない。

1. 支援主体3者以上が、正規化区分と事件固有回答のどちらを必要とするか評価
2. JINSとLINEヤフーの架空アダプターで、対象条件・未通知・推計件数を誤表示しないことをテスト
3. `impactSignals` が初期トリアージに必要か、センシティブすぎないかを確認
4. v1からv2へ自動変換せず、新旧の意味差を明示

## H6の判定

- 状態: **一部支持**
- 支持する証拠: 3事案で、公開資料、対象関係、通知状態、証拠種類、参加意思という共通層を定義できる
- 反証・懸念: 対象関係、件数単位、個別通知方針、公開状態が大きく異なる。単一の固定質問票は成立しない
- 次の検証: 支援主体面談で、事件固有回答と正規化結果の両方が必要か確認する
