# Morashiter ユビキタス言語

## 2026-11-10追記：購入前確認とSandboxデモ

ユーザーが採用したシナリオを記録する。Chrome拡張0.2.0は現状維持。デモ店舗・AIメモ・決済は**実装ドラフトを作成し、実プロバイダの通し確認待ち**。実装順・テストデータは[あおぞらデモ実装計画](../plans/aozora-ai-paypal-demo-plan.html)に置く。以下の2026-10-03本文は既存領域の設計基準として残す。

| 用語 | 意味・境界 |
| --- | --- |
| 公表情報レコード | 現行JSONの1つのID。事案の実数と同義ではない。INC-007とINC-016は同一事案の続報だが現在は別IDであり、拡張は2と表示する。統合は保留。 |
| デモ店舗（Aozora Goods） | あおぞら雑貨店という架空店舗。既存拡張のDEMO-001と同じホスト・資料内容を使用する。 |
| デモ資料（DemoNotice） | 作成者が管理する架空の固定資料。実企業の公式発表でも、本番Incidentでもない。 |
| AI購入前メモ（PurchaseMemo） | 資料から公表内容・不明点・一般的注意を整理する補助情報。掲載審査、企業評価、購入推奨、支払承認ではない。 |
| 購入判断 | 利用者が購入を進めるか見送るかを決める行為。AIが代行しない。 |
| 支払承認 | 利用者によるPayPal Sandbox画面上の承認。注文作成やメモ閲覧とは異なり、capture完了でもない。 |
| 決済確定（capture） | サーバーがPayPalからCOMPLETEDと注文・金額・通貨等の整合を確認した状態。Sandbox内の模擬処理で実際の請求・配送はない。 |
| 結果不明 | 通信断等で外部処理の結果が不明な状態。失敗や未決済と決めつけず同じ注文を照会する。 |

AIが扱う架空資料と実企業の公表情報を混在させない。「PayPalなら漏えいを防げる」「この店舗は安全」等の保証へ言い換えない。

2026-10-03 時点。ここでの「確定」は**仕様上の扱い**を指し、事件の事実や法的責任を Morashiter が独自に認定する意味ではない。既存の [テーブル案](../design/mrst-table-proposal.html) は未実装の論理設計案であり、列名・コード値はマイグレーション前に検証する。

## 事件・根拠・確実性

| 用語 | 定義と表示ルール |
| --- | --- |
| インシデント（Incident） | 同一の事象を追跡する単位。ニュース記事の本数、企業名、URLとは一対一にしない。続報・訂正は同じ Incident の新しい版として扱う。 |
| 一次資料 | 当該企業・団体、所管機関等が事象について直接公表した原資料。発行主体、URL、資料上の日付、取得日時、内容の版を保持する。ニュース記事は原則として発見・照合用の補助資料であり、それだけで一次資料確認済みにしない。 |
| 資料のスナップショット | 取得時点の本文・メタデータ・ハッシュ。原文が更新されたら旧内容を上書きせず新しいスナップショットを残す。原資料は非公開領域に保存する。 |
| 漏えい確定 | 一次資料が「漏えいした／流出を確認した」と明示する**対象範囲**に限る表現。システムの `confirmed` は資料の記述区分であり、各利用者の被害、責任、請求権の確定ではない。 |
| 漏えい可能性 | 一次資料が「漏えいした可能性」「閲覧可能な状態」等としており、漏えい自体を確認していない区分。`possible` を `confirmed` に言い換えない。調査中・不明はそれぞれ `under_investigation`・`unknown` と区別する。 |
| 対象可能性 | 公表条件と利用者が端末内で把握した状況からの初期整理。個人の漏えい確定や法的判断ではない。事件全体の `disclosure_status` と混同しない。 |
| 訂正・撤回 | 以前の公開内容を変える運用判断。理由と根拠を残し、承認済み版を直接編集しない。撤回後のCDN上の残存も確認対象とする。 |

資料上の発生日、初回公表日、当該版の根拠資料の公表日、システム取得日時は別の値。日付が不明な場合は推定日、HTTP Date、取得日時で補完しない。複数資料が矛盾する場合は差分を残して人手レビューへ送る。

## 数値と集計

| 用語 | ルール |
| --- | --- |
| 件（`records` 等） | 情報レコード・契約・取引等、資料が示す単位をそのまま保持する。「件」を「人」と換算しない。日本語の「件」は文脈依存なので対象も併記する。 |
| 人（`persons`） | 人数を表す。アカウント数やメールアドレス数から推計しない。 |
| アカウント（`accounts`） | アカウント数を表す。一人が複数アカウントを持ち得るため人数にしない。 |
| その他の単位 | 団体数は `organizations`。単位不明は `unknown` とし、数だけを掲載しない。 |
| 影響規模（Impact） | 数値、単位、対象範囲、確定性（`exact` / `approximate` / `at_least` / `at_most` / `unknown`）、資料の原表記、根拠資料を一組で管理する。異なる単位・対象範囲・重複の有無が不明な値を合算しない。 |
| 未集計 | 集計がまだ完了していない、または公開可能な実測集計がない状態。架空のゼロや仮値を表示しない。`0` は対象がゼロと確認された場合のみ使う。 |
| 未算定 | 重大度・ランキングなど、算定基準または評価結果が未確定の状態。数値のNULLを0点と扱わない。 |

「希望者数」「購読者数」は漏えい被害者数ではない。希望ボタンは重複抑制された押下数であり、実人数の証明でも訴訟参加者数でもない。購読者数は本人確認済み（`confirmed`）の購読に限定する設計案である。公開前に集計定義、単位、対象期間を表示できるようにする。

## 収集・審査の語彙

| 用語 | 定義 |
| --- | --- |
| 媒体コード（`adapter_code`） | 許可済み取得元の**抽出アダプター識別子**。`crawl_sources` の `source_type`（`news` / `official` / `disclosure`）や `crawler_code`（`msnc` / `msic`）とは別。媒体名、ホスト、抽出版を固定設定と対応させる。記事中の文字列をコードや実行ファイル名として採用しない。具体的なコード値は媒体の利用条件確認時に決める。 |
| msnc | ニュース記事を発見・安全に取得・抽出し、非公開保存して候補を渡す処理。ニュース単独で企業同定や公開を確定しない。 |
| msic | 企業等の公式発表を追跡・取得する処理。旧称 `msuc` は新規仕様・コードで使わない。 |
| msjd | 保存済み資料について2つ以上の独立したAIで該当性・事実・根拠を検証する処理。完全一致かつ重大な不確実性がない候補を自動承認し、それ以外をadminへ引き渡す。 |
| msad / admin | 人手レビューが必要な候補の資料・表現・訂正を確認し、公開可否を決める管理機能。 |
| msgn | 承認済み版だけから静的公開物を作成し、オブジェクトストレージとCDNへ反映する処理。 |
| 承認方式 | `ai_consensus` は2つ以上の独立したAIによる完全合意と根拠検証を満たす自動承認。`manual` は管理者の人手承認。どちらも版の `approved` へ至る正式な経路。既存テーブル案の人手側の値 `human` は実装前に `manual` へ整合させる。 |
| 審査ステータス | 候補版の `draft`（編集中）、`evaluating`（合議評価中）、`review_required`（人手確認待ち）、`approved`（合議または管理者が承認）、`rejected`（掲載しない）、`withdrawn`（承認・公開の撤回）。これは[テーブル案](../design/mrst-table-proposal.html)の候補値であり、**公開配信の成功状態とは別**。 |

この文書の「公開」は、承認済み版に基づく静的成果物のアップロードとCDN反映が完了し、公開版ポインターが切り替わった状態をいう。`approved` だけでは「公開済み」と表示しない。

## 参照と優先順位

根拠は[テーブル案](../design/mrst-table-proposal.html)、[msnc実装計画](../plans/msnc-crawler-implementation-plan.html)、今回の明示指示。前版の「人手承認必須／`ai_consensus` 不採用」を撤回し、**2つ以上の独立したAIの完全合意による `ai_consensus`、または管理者による `manual`** を正式な承認経路とする。合議の不一致、一次資料の欠落、訂正・撤回・重大な削除、設定された重大インシデントの要レビュー条件に該当する場合は自動承認しない。承認は配信完了を意味しない。変更には人間の設計レビューが必要。
