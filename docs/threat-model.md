# 脅威モデル v1

更新日: 2026-09-30

## 対象範囲

対象は、現在の非公開Webプロトタイプである。

- 被害者向け事件案内・対象可能性確認
- 端末内の証拠チェック・自由記述メモ・参加意向
- 利用者自身による全記録および最小共有パケットの書き出し
- 支援主体向け画面での最小共有パケットの端末内読込み・集計
- 識別子を含まないユーザビリティ検証結果の書き出し

将来のメール登録、サーバー保存、支援主体への自動転送、正式受付、委任・授権、証拠原本受領は対象外であり、別の脅威モデルなしに追加しない。

## 現在のデータフロー

```text
公式一次情報 ──> RightsRelay配信サーバー ──> 利用者ブラウザ
                                               │
                                               ├─ 端末内保存
                                               ├─ 本人用JSON
                                               └─ 最小共有JSON ── 利用者が自分で移動
                                                                          │
                                                                          v
                                                            支援主体ブラウザ内で集計
                                                                          │
                                                                          └─ 件数だけのJSON
```

RightsRelay配信サーバーは画面と静的資産を返すだけで、POST等の書込み要求を受け付けない。利用者回答と読込みファイルを受信するAPIは存在しない。

## 守る資産

| ID | 資産 | 現在の場所 | 重要度 |
|---|---|---|---|
| A1 | 対象確認の回答 | 利用者ブラウザ | 高 |
| A2 | 証拠保有状況 | 利用者ブラウザ／共有パケット | 高 |
| A3 | 自由記述メモ | 利用者ブラウザ／本人用書出し | 重大 |
| A4 | 参加意向 | 利用者ブラウザ／共有パケット | 高 |
| A5 | 支援主体が読み込んだ複数パケット | 支援主体ブラウザのメモリ | 重大 |
| A6 | 事件情報・判定規則 | 配信ソース | 高 |
| A7 | 同意状態・境界表示 | 配信ソース／利用者ブラウザ | 高 |
| A8 | 支援主体の真正性 | 将来の提携台帳 | 重大 |

## 信頼境界

1. **配信境界** — 配信されたコードが改ざんされれば、端末内データを読み取れる。
2. **ブラウザ境界** — 同一端末の利用者、拡張機能、マルウェア、共有プロファイルからは完全に隔離できない。
3. **ファイル境界** — JSONを書き出した後の保存先・送信先・バックアップはRightsRelayの管理外となる。
4. **支援主体境界** — 読込み先が本物の弁護士・団体であることを現行試作は確認しない。
5. **一次情報境界** — 企業発表は企業の調査結果であり、裁判所・行政による事実認定とは異なる。

## 想定する攻撃者

- 不特定の外部攻撃者
- 企業・支援主体・RightsRelayを装うフィッシング実行者
- 偽パケットで人数を水増しする者
- 悪意ある、または侵害されたブラウザ拡張機能
- 端末を共有する同居人・同僚
- 依存パッケージや配信経路を侵害する攻撃者
- 権限を越えて情報を閲覧しようとする将来の運営者・提携先

## 脅威と現在の対策

| ID | 脅威 | 現在の対策 | 残余リスク |
|---|---|---|---|
| T1 | XSSや改ざんコードが端末内回答を外部送信 | `connect-src 'none'`、外部画像・フォーム・フレーム・Worker禁止、外部通信APIなし | インラインスクリプト許可が必要。配信コード自体が改ざんされた場合の影響は残る |
| T2 | 第三者タグ・解析SDKが行動を収集 | 解析SDK・広告SDKなし。CSPで外部スクリプトと通信を禁止 | 将来SDKを追加すると保証が崩れる |
| T3 | POSTやフォームで機微情報を送信 | GET/HEAD以外を405で拒否。`form-action 'none'` | 別ドメインの偽サイトは防げない |
| T4 | 悪意あるJSONが未知項目や自由記述を混入 | 完全な許可リスト、型・列挙値・事案版検証、未知項目はファイル単位で拒否 | JSONパーサーやブラウザ自体の脆弱性は残る |
| T5 | ファイル名やパスから個人情報を取得 | ファイル名を表示・保存・集計しない | OSのダウンロード履歴等は管理外 |
| T6 | 同一パケットの重複、水増し | UUID重複除外。件数は法的事実と扱わない | 1人が複数UUIDを作るSybil攻撃は防げない |
| T7 | 偽の支援主体へ利用者がファイルを送る | 現行は自動転送なし。正式提携前の実データ移転を禁止 | 利用者自身による誤送信は防げない |
| T8 | 共有端末・端末紛失でローカル記録が露出 | 保存場所を明示し、削除機能を提供。通知・サーバーには残さない | OSアカウントやディスクが侵害されれば読まれる可能性 |
| T9 | 外部リンクから参照元が伝わる | `Referrer-Policy: no-referrer` | 外部サイト側のフィッシングや内容変更は防げない |
| T10 | iframe埋込みによるクリックジャッキング | `frame-ancestors 'none'` と `X-Frame-Options: DENY` | ブラウザ外の画面偽装は防げない |
| T11 | 古い事件情報・判定規則による誤案内 | 出典・確認日・規則版を表示 | 更新監視と専門家レビューは未実装 |
| T12 | 依存パッケージの侵害 | lockfile固定、ビルド・監査・レビュー | 署名付きビルド、SBOM、継続監視は未実装 |
| T13 | 小人数集計から個人を推測 | 現在は非公開・端末内のみ。外部公開しない | 公開版には5件未満の抑制または丸めが必要 |
| T14 | 「対象可能性」が法的資格・請求権と誤解される | 企業発表上の条件だけと明記し、法的判断を否定 | 利用者テストと法律家レビューが必要 |

## 配信時の強制ルール

本番レスポンスに以下を設定する。

- `Content-Security-Policy`
  - `connect-src 'none'`
  - `form-action 'none'`
  - `frame-ancestors 'none'`
  - `frame-src 'none'`
  - `object-src 'none'`
  - 外部スクリプト、外部画像、外部フォントを不許可
- `Referrer-Policy: no-referrer`
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Cross-Origin-Opener-Policy: same-origin`
- `Cross-Origin-Resource-Policy: same-origin`
- カメラ、マイク、位置情報、決済、USB等をPermissions Policyで不許可
- HTMLを `Cache-Control: no-store`
- HTTPのGET/HEAD以外を405で拒否

フレームワークが生成する初期化コードのため、現時点の `script-src` には `'unsafe-inline'` が残る。これは既知の残余リスクであり、実データをサーバーで扱う版ではnonceまたはハッシュ方式へ移行できるか検証する。

## 自動検査

ビルドごとに以下を確認する。

- 本番相当URLでは `connect-src 'none'` になっている
- フォーム送信・フレーム埋込み・Object埋込みが禁止されている
- POST要求が405になる
- クライアントコードに `fetch`、`XMLHttpRequest`、`sendBeacon`、`WebSocket` がない
- 共有パケットの未知項目・同意改変を拒否する
- 同一パケットIDを重複集計しない
- 支援主体向けページがサイト全体の共有画像を誤継承しない

静的検査は難読化コードや依存パッケージ内の通信を完全には証明しない。外部セキュリティレビューでは、ブラウザの通信ログと配信成果物を別途確認する。

## 実データ実証前のセキュリティゲート

1. データフロー図と資産一覧を実装に合わせて更新した
2. 運営主体・セキュリティ責任者・事故連絡先を定めた
3. 支援主体の認証、送信先固定、権限管理を実装した
4. 保存時・通信時暗号化と鍵管理をレビューした
5. 同意・提供・閲覧・削除の監査証跡を改ざん耐性のある形で保持した
6. 保存期間終了、撤回、提携終了時の削除を自動試験した
7. バックアップからも削除できることを確認した
8. 依存関係監査、秘密情報検査、SAST、侵入テストを実施した
9. CSPから `'unsafe-inline'` を除けるか評価し、残す場合は明示的にリスク受容した
10. 事故対応手順、本人・監督機関・提携先への連絡判断を演習した
11. 少人数セル抑制とSybil対策を実装した
12. 第三者のセキュリティ担当者が重大所見なし、または対策済みと判定した

## 現時点の結論

現在の試作は、端末内整理と架空・本人持参ファイルによる評価に限定する。通信を技術的に遮断しているため、中央集約サービスの安全性を証明するものではない。実データをサーバーで集める設計へ移る時点で、この脅威モデルを全面更新する。
